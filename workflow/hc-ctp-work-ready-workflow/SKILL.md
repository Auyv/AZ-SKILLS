# 鸿泉 MPU 工程准备与交付工作流

适用于以产品 XML manifest 管理多个 MPU 仓库的开发任务。目标是让每个任务在独立工作目录中获得可验证的代码基线，随后再等待用户下达具体实现要求。

## 输入与边界

开始前确认以下信息；缺少会影响拉取目标或覆盖风险时再询问用户：

- 产品 XML manifest 的绝对路径。
- 本任务独立 workspace 的绝对路径与任务用途。
- 用户指定的拉取入口，例如 `git_pull_xml`，及其参数约定。

完整读取当前环境提供的全局规则、工作区与目标仓库的 `AGENTS.md`。涉及分支、提交或 MR 时，再读取适用的 Git 规则。

## 准备流程

### 1. 隔离工作空间

- 使用工作区父目录下以任务标识命名的独立子目录，例如 `C:\HQ_Workspace\<project>\workspace\<YYYYMMDD>-<task>`。
- 不复用其他任务目录，不将生成物写入共享父目录。
- 目标目录已存在时，先检查其内容和 Git 状态；存在无关文件、未提交修改或来源不明的仓库时停止并请用户决定，禁止覆盖或清理。
- 用户明确指定目录规则时，将其记录到适用范围内的 `AGENTS.md`；未获要求不自行创建协作文档。

### 2. 按 manifest 拉取代码

- 先确认 XML 文件存在且可解析，记录其产品标识、项目路径和 `revision` 覆盖项。
- 用户给出 `git_pull_xml` 或其他脚本入口时，优先直接使用该入口；只做必要的用途和参数核对，不用自行拆解的 clone/fetch 命令替代。
- 未指定拉取入口时，说明缺少的工具或参数；不得猜测私有仓库地址、分支或凭据。
- 拉取失败时保留原始错误、已创建目录和已完成仓库范围，避免通过删除 workspace 掩盖失败。

### 3. 交付可开发基线

- 对本次相关仓库检查 `git status --short`、当前 HEAD/分支与 manifest 指定 revision；报告任何未提交改动、拉取遗漏或分支偏差。
- 找到并读取各仓库的 `AGENTS.md`，确认构建入口、测试方式和额外约束。
- 汇总 workspace、manifest、已拉取仓库和异常项。只有拉取与基线检查完成后，才向用户确认“准备好”并等待具体工作内容。
- 在用户给出具体任务前，不修改业务代码、产品配置、manifest、构建脚本或远端分支，也不启动无关构建。

## 收到具体开发任务后

1. 先识别具体文件所属仓库、原目标分支和相关 `AGENTS.md`；处理多仓库修改时维护清晰的仓库映射。
2. 优先复用用户指定的源分支或已有开放 MR；两者均不存在时，才从原目标分支创建独立任务分支实施最小修改。保持编码和换行，并按任务风险执行构建、测试或静态检查。
3. 仅提交本仓库相关文件并推送任务分支，再创建“任务分支 → 原目标分支”的 MR。
4. **不得直接向任何远端目标分支推送、快进或合并。** 用户说“同步”或“合并”时，默认创建或更新 MR；CI 通过后仅报告状态，等待人工审核和合并。
5. 用户要求用测试分支验证 CI 时，可临时调整其明确指定的 manifest；验证 XML 与差异，除非用户要求，不提交该临时修改。

## 停止条件

在 manifest 路径、workspace 路径、拉取入口或其参数不明确；目标目录存在可能被覆盖的数据；仓库认证失败；或 XML 与实际拉取结果不一致时，停止并向用户报告事实与所需决定。不得删除目录、重置仓库或猜测分支来继续。
