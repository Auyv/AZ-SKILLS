## 原始描述

> bsc_hse 组件代码中不应该有动态库的加载代码。组件代码应该是抽象的逻辑代码封装，如果增加了动态库加载代码，这将表示组件只能在 Linux 系统上使用。正确的方式应该是组件框架定义虚接口类，然后在 RTE 层根据项目的实际情况实现虚接口导入给组件。在本次项目中应该是 RTE 层加载动态库并封装成 bsc_hse 接口导入，app 层再调用 bsc_hse 实现 SPC 接口的衔接。

## 问题场景

当前 `framework/bsc_hse/common/bsc_hse.c` 直接包含 `dlfcn.h`，并实现 `dlopen`、`dlsym`、`dlclose` 以及动态库句柄生命周期管理。公共组件因此感知 Linux 动态库机制，破坏组件的平台无关性和分层边界。

## 期望行为

1. `framework/bsc_hse` 只保留平台无关的业务逻辑、对象管理、参数校验、串行化和统一错误语义。
2. BSC HSE 定义稳定的供应商能力虚接口（C 操作表），通过显式注册/注入获得实现。
3. `rte_component/rte_hse` 根据当前项目环境加载 Linux 动态库，解析供应商符号，封装为 BSC HSE 虚接口并注入组件。
4. app 层负责初始化 RTE、调用 BSC HSE，并把 BSC HSE 能力衔接到 SPC 生成接口。
5. BSC HSE 源码和组件构建目标不直接依赖 `dlfcn.h`、`dlopen`、`.so` 路径或 `-ldl`。

## 影响分析

- 现有动态库加载、测试入口和卸载逻辑需要从 BSC HSE 迁移至 RTE。
- BSC HSE 初始化契约需要改为“先注入虚接口，再初始化组件”。
- CIU98 供应商适配的归属需要从组件内部实现调整为 RTE 项目适配实现。
- app/SPC 集成层需要按 `app -> BSC HSE -> 注入接口 -> RTE/供应商库` 的方向组装依赖。
- fake 测试继续直接注入操作表，用于验证组件平台无关逻辑。

## 经验沉淀

- 根因：组件抽象边界与项目运行时适配边界混淆，平台加载机制下沉到了公共组件。
- 预防建议：公共组件只声明依赖接口；操作系统、动态库、硬件 SDK 和项目配置均由 RTE 或 app 组合根实现，并通过依赖注入接入组件。
