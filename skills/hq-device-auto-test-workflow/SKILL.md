# Linux 设备功能自动化测试工作流

把设备侧功能模块的验证固化为一条流水线：
**功能点拆解 → 独立测试单元 → 声明式用例配置 → 统一调度执行 → JSON 结构化报告**。
人工只触发一条命令，机器产出可归因的结论（用例级 PASS/FAIL + 逐帧证据）。

方法论已在一个完整真机项目上验证通过（HJ1239 协议库，01/02 套件 8 用例全 PASS）。

## 核心原则

- **先定证据，再写用例**：每个功能点先回答"用什么原始数据判定通过"（协议帧/日志/属性/文件）。判定不了的先补观测插桩，插桩必须可关闭且不影响被测行为。
- **单进程原则**：被测服务一个进程 + 测试进程一个（driver 与协议对端模拟器合并为单一二进制 serve 模式）。测试进程内部禁止多线程竞态送数——诊断/观测与激励共用线程时会互相阻塞。
- **用例与引擎分离**：`cases.json` 声明激励与断言，runner 只负责调度与判定；新增功能点只加用例不改引擎。
- **环境故障与产品缺陷分开判定**：环境异常（掉线、磁盘满、服务未起）标 ERROR/BLOCKED，绝不计入 FAIL；FAIL 必须能归因到具体证据。
- **豁免必须显式**：对被测机制导致的预期偏差（如采集掩码快照产生的"预热包"），在用例中显式声明豁免及理由，禁止静默忽略，也禁止为此改产品代码。

## 工作流（五阶段）

### 阶段 0：环境基线

一次性：确认交叉编译链（通常 docker 容器 + arm 工具链）、adb 通路、设备上被测服务的部署路径与重启方式。
每次执行前自检（写入 run_all 入口）：adb 设备在线 → 部署目录磁盘可写（`touch` 写测，ubifs 满盘不报错只写入失败）→ 被测服务 pid 存活。

### 阶段 1：功能点拆解

输入：`az-sdd/spec`、`az-sdd/arch` 文档（没有则从接口头文件 + 需求描述提炼）。
每个功能点产出一张单元卡片：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| 功能点 | 可独立判定的最小行为 | 登入流水号按步长递增 |
| 激励 | 驱动器注入什么 | 显式 Logout→Login |
| 证据 | 对端收到什么 | 0x01 帧的 seq 序列 |
| 判定规则 | 归属哪种 kind | login_sequence |
| 归属套件 | 按被测通道/功能分组 | 02_stdReport |

拆解粒度：一个功能点 = 一个断言维度。不把"类型正确"和"条数正确"塞进同一用例。

### 阶段 2：测试单元实现

- **驱动器（driver）**：模拟客户端应用侧，向被测库推送输入（周期数据、触发器、控制命令）；送数按墙钟秒对齐补漏，不按"上次 +1s"漂移。
- **对端模拟器（TSP）**：TCP server，收帧逐帧校验（帧结构 + 签名/BCC），发应答，每帧写 JSONL 证据（`{event:"frame", channel, cmd, time, monotonic_ms, items:[{type, raw:{...}}], structure, signature}`）。
- 两者合并为单一测试二进制（`serve --duration N --log <dir> --set-int ID=V ...`），`driver_args` 由用例注入。
- 测试专用插桩用测试宏隔离（如 `#ifdef XXX_TEST`），并保证生产构建（`-Werror`）下编译通过（未使用参数补 `(void)`）。

### 阶段 3：用例配置（cases.json）

模板见 [assets/cases.template.json](assets/cases.template.json)，schema 详解与判定规则库见 [references/patterns.md](references/patterns.md)。
要点：每个用例声明 `id / kind / duration / driver_args / expected`；基准值必须**实测校准**并注明测量来源与容差（如 `expected_records=59±2`，注明"60s 窗口实测"）。

### 阶段 4：统一调度（run_all）

参考实现：`hqt420_s11` 任务仓 `s32k312_asr1803/lib/hc_pm_msg_hj1239/tester/run_all.py`（分支 `codex/jpz@master`，含 run_all.sh/.bat 人工入口与 tools/ 构建脚本）。新项目按该骨架改造，要点：

1. 自检失败 → 退出码 2，不跑测试。
2. 部署 = 推产物 + 重启被测服务 + 等就绪（等 pid 消失/重现 + 沉降，不用固定 sleep）。
3. 套件依序执行，过程输出**实时流式打印**（带秒级前缀），单套件超时可配（默认 ≥1500s，超时终止并标 ERROR）。
4. 结束后汇总各套件 JSON → 顶层 `run_all-<时间戳>.md/.json`；退出码 0=全 PASS / 1=有用例 FAIL / 2=环境错误。

### 阶段 5：报告与归因

- 三层产物：套件 JSON 报告（用例级结论+摘要证据）→ 逐用例证据目录（frames.jsonl / collector.txt）→ 顶层汇总。
- 判定语义固定：`PASS / FAIL / INCOMPLETE / BLOCKED / ERROR`；BLOCKED 必须写明缺什么（如 baseline 未建立）。
- 每条结论可回溯到 frames.jsonl 的具体帧。

## 陷阱清单（真机实测摘录，全表见 references/pitfalls.md）

| 症状 | 根因 | 对策 |
| --- | --- | --- |
| 数据量突然归零 | 挂载点掉线退化为写满盘，队列 ENOSPC | 阶段 0 写测自检；判定层分环境错误 |
| 下个用例混入上用例数据 | 磁盘队列残留以补发形式串扰 | 每用例前清队列文件 |
| 整包字段全无效、呈固定周期 | 观测扫描 RPC 阻塞激励线程，漏秒照常出包 | 观测可关闭；内容敏感用例默认关 |
| 首个数据包类型不符 | 被测库配置快照机制（预热包） | 判定层显式豁免 + 记录 |
| 对端收到登入即断开 | 断连阈值把握手帧计入 | 只统计业务数据帧 |
| 断连重连验证不了 | 中间件对对端断连不敏感（FIN/RST 均 300s+ 无感） | 记录观察项；用显式控制命令驱动同一状态机 |
| 正常重启被误判掉线 | 固定超时太短（高负载重启 >50s） | 超时要宽（≥120s）+ pid 就绪等待 |
| 判定永远差一点点 | 基准值拍脑袋 | 实测校准 + 容差 + 来源注明 |

## 边界

- 需要 root 刷机、改分区、烧写的操作不在本流程内，先征得用户同意。
- 性能/压力/长稳测试不是本流程范围。
- 一次会话内设备掉线 ≥2 次：停止执行，向用户报告环境风险（线缆/供电），不要重试硬扛。
- 测试代码必须入库（产物用 `**/out/` 类规则忽略，源码纳入版本控制）；改动做好 commit 记录，产品代码修复与测试侧修复分开提交。
