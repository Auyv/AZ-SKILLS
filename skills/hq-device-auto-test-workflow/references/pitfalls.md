# 真机陷阱清单（症状 → 根因 → 对策）

来源：HJ1239 真机测试项目（2026-09-29，hqt420_s11 任务仓）实测。通用性强，适用于任何
"Linux 设备 + 嵌入式服务 + 协议库 + adb 通路"的自动化功能测试。

## A. 环境类

### A1. 挂载点退化导致数据量归零（最隐蔽）
- **症状**：套件前几个用例正常，之后全部 `frames=0`；产品代码未动。
- **根因**：设备 eMMC 掉线，挂载点退化为 ubifs 根分区且已写满；插件磁盘队列写入 ENOSPC，秒数据无法入队。`df` 类工具可能看不出（ubifs 满盘仍显示异常），要 `stat -f` 对比 dev 号 + `touch` 写测。
- **对策**：阶段 0 自检必须做写测；runner 判定层把"磁盘不可写"归为环境错误（exit 2），不产生 FAIL。
- **非破坏恢复**：把队列目录迁到可用分区（改 ini 的 queue_path），备份原配置。

### A2. 用例间磁盘队列残留串扰
- **症状**：下一用例开头收到上一用例的数据类型（以 0x03 补发形式）。
- **根因**：磁盘队列文件跨用例残留，重新登入后作为补发上报。
- **对策**：runner 每用例前 `rm -f <queue_dir>/*.fq`（绝对路径校验），并等被测服务就绪。

### A3. 服务重启就绪竞态
- **症状**：重启服务后建通道失败（`channel-add failed`）或零数据。
- **根因**：固定 sleep 3s 不够，插件尚未加载完成。
- **对策**：等 pid 消失（≤15s）→ 等 pid 重现（≤30s）→ 再沉降 8s。adb 命令超时放 ≥120s（高负载下重启实测 >50s）。

### A4. 设备 USB 闪断
- **症状**：adb `device not found`，PnP 中设备消失；有时设备自行重启（uptime 归零）。
- **对策**：runner 在自检和每套件失败后检查设备在线；一次会话 ≥2 次闪断即停止并报告（线缆/供电风险）。设备重启后注意 uptime 判断 + 等待服务自启完成。

### A5. 主机侧工具链
- Git Bash 会把 `/mnt/...` 转成 Windows 路径：所有 adb/ssh 参数路径需 `export MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'`。
- Grep 类工具默认遵守 `.gitignore`：若仓库忽略了 tester/ 目录，搜索会漏文件，用 `rg --no-ignore`。
- 后台长命令用工具的 run_in_background，`nohup ... &` 会被 adb 会话断连杀掉。
- **Git Bash heredoc 会把反斜杠改写为正斜杠**（实测 `\s` → `/s`，正则 `r"\s*"` 静默失配）：heredoc 内嵌脚本避免反斜杠转义，用 `[ \t]*`、`chr(10)` 等替代，或写临时 .py 文件再执行。

## B. 观测侵入类

### B1. 观测扫描阻塞激励线程（整包无效值）
- **症状**：数据包呈固定周期（如每 5s 一个）整包 19/19 字段全无效（65535/254/0xFFFFFFFF）。
- **根因**：诊断扫描逐个读 120 个属性（每项一次 RPC），阻塞了驱动的送数线程；被测库在该秒拿不到新鲜样本，但采集节拍照常出包，整包打无效标记。
- **对策**：所有观测/诊断插桩必须可关闭（`--diag-trace-ms 0`）；内容敏感用例（逐字段比对、条数比对）默认关闭。送数改为按墙钟秒对齐补漏（消总数偏差），但解耦才是根治。
- **验证方式**：修复前 17/59 包无效 → 修复后 0/59。

### B2. 字段级 vs 包级无效要先分辨
- **症状**：某字段 65535。
- **先核实**：是该字段单独无效（数据通路问题），还是整包无效（B1）？逐包统计 `invalid/total` 再下结论。

## C. 判定机制类

### C1. 预热包（配置快照机制）
- **症状**：每用例首包的数据类型/内容与配置不符，之后全对。
- **根因**：被测库在通道 init 时快照采集配置，应用侧随后的配置写入要到下一采集周期才生效；打包器按队列记录自身的类型出包。
- **对策**：用例侧显式豁免（`allow_warmup: true` + `warmup_reason`），判定层把"登入后首帧 ±1500ms"定义为预热窗口，单独记录不静默。**不改产品代码迁就测试**。

### C2. 断连阈值把握手帧计入
- **症状**：对端收到登入帧立即断开，应答发不出，用例永不通过。
- **根因**：`disconnect-after N` 统计所有帧，登入帧就是第 1 帧。
- **对策**：只统计业务数据帧。

### C3. 中间件不感知对端断连
- **症状**：对端 FIN 甚至 RST（SO_LINGER 0）断开后，被测库会话状态 300s+ 恒为 Connected，重连不触发。
- **定性**：这是 SC/链路中间件行为，不是被测库缺陷；自动化验证此路径被阻塞。
- **对策**：记录为观察项（写入用例 baseline_note 与提交说明）；改用客户端显式控制命令（ChannelControl Logout→Login）驱动同一状态机完成验证（如流水号递增）。

## D. 基准与流程类

### D1. 基准值拍脑袋
- **对策**：条数/字段值基准必须实测校准，注明测量窗口与来源，给容差（±2）。首个包可能包含登入前的偏移，用第 2 个有效包做字段基准核对。

### D2. 测试代码入库
- `.gitignore` 整体忽略 `tester/` 会导致测试源码失管：改为产物级规则（`**/out/`、`*.o` 等）。
- 注意 `.gitignore` 尾行缺换行符的合并陷阱。
- 产品代码修复与测试侧修复分开 commit；vendor/第三方目录零改动约定，阻塞级缺陷的例外修复要在提交说明中注明理由与验证数据。

### D3. 观测与验证分离
- 判定只依赖 frames.jsonl 证据；collector.txt（驱动/服务日志）只做归因。判定函数必须可离线回放（输入证据 + 用例配置 → 结论），便于复跑规则而不重跑设备。
