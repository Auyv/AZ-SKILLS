# AZ-SDD-ARCH

技术规范编写（可选）- 为研发人员、测试人员和后续 AI 实现流程创建软硬件技术契约。

## 职责边界

| 问题 | spec 回答 | arch 回答 |
|------|-----------|-----------|
| 给谁用 | 产品用户、业务负责人、验收者 | 研发人员、测试人员、后续 AI 实现流程 |
| 关注什么 | 做什么、谁使用、怎么操作、如何验收 | 怎么实现、怎么部署、怎么验证、依赖什么软硬件 |
| 主要产物 | 用户目标、使用场景、输入输出、验收标准、人工测试用例 | 技术选型、模块边界、API、数据模型、部署/运行环境 |
| 禁止写什么 | 技术选型、接口设计、数据库表结构、部署架构 | 新增产品需求、改变验收口径、替用户决定功能行为 |

> 冲突处理：当 spec 与 arch 冲突时，不能默认用 arch 覆盖 spec。spec 是用户价值契约，arch 是实现契约；如果技术方案要求改变产品行为或验收标准，先回到 spec 修改并重新审核。

## 规范类型

| 类型 | 路径 | 用途 |
|------|------|------|
| 项目级技术架构 | `az-sdd/ARCH.md` | 记录全局技术栈、软硬件环境、部署方式、跨功能约束和技术规范索引 |
| 功能/模块级技术规范 | `az-sdd/arch/{ID}-{MODULE}-{NAME}.arch.md` | 记录某个功能或模块的技术设计、接口、数据模型、验证条件和风险决策 |

## 执行步骤

### Step 1: 检查环境

```
1. 检查 az-sdd/ 目录是否存在
   → 不存在：提示先执行 /az-sdd-init
   → 存在：继续
2. 判断 arch 类型
   → 项目级：读取 INIT.md、SPEC.md、已有 ARCH.md（如存在）
   → 功能/模块级：读取对应功能规范（spec），确认功能目标、用户流程、验收标准和非功能需求
3. 检查 .config/naming.yaml 获取编号规则
```

### Step 2: 分析技术复杂度

从功能规范中提取产品侧输入，只把它作为技术设计的约束来源：

```
📋 从功能规范提取的实现约束：

| 要素 | 内容 |
|------|------|
| 功能目标 | {GOAL} |
| 用户流程 | {USER_FLOW} |
| 输入输出 | {INPUT_OUTPUT} |
| 验收标准 | {ACCEPTANCE} |
| 非功能需求 | {NON_FUNCTIONAL} |
| 外部依赖/硬件环境 | {DEPENDENCY_OR_HARDWARE} |

🤔 技术复杂度评估：
- 模块数量：{N}
- 外部依赖：{M}
- 软硬件约束：{HW_SW_CONSTRAINTS}
- 技术风险：{RISK}

建议：{SUGGESTION}
```

### Step 3: 判断是否需要独立技术规范

**如果判定为简单功能**：
```
💡 这个功能比较简单，没有发现必须独立决策的技术议题。
   可跳过独立 arch，仅依据 spec 的功能契约和轻量实现影响提示开发。

   如有需要，可随时使用此 SKILL 创建独立技术规范。
```

**如果判定为复杂功能**：
```
📝 检测到此功能涉及复杂技术决策，建议创建独立技术规范。

需要处理的技术议题：
1. {TOPIC_1}
2. {TOPIC_2}
3. {TOPIC_3}

是否继续？
- [继续] 创建技术规范
- [跳过] 保持现状，只使用 spec 中的轻量实现影响提示
```

### Step 4: 收集技术信息

**必须询问用户**：

1. **涉及哪些软硬件组件？** - 前端、后端、数据库、设备、固件、外部服务、网络环境？
2. **技术选型有没有偏好或限制？** - 有没有必须使用/禁止使用的语言、框架、数据库、协议、硬件？
3. **模块边界如何划分？** - 哪些模块负责输入、处理、存储、展示、设备交互？
4. **接口和数据如何流转？** - API、文件格式、消息协议、数据库模型、缓存策略？
5. **部署与运行环境是什么？** - 本地、服务器、容器、嵌入式设备、操作系统、启动/关闭方式？
6. **测试验证入口是什么？** - coder 如何自动验证？tester 如何启动应用并执行人工验收？

### Step 5: 生成规范

```
项目级文件：az-sdd/ARCH.md
功能/模块级文件：az-sdd/arch/{ID}-{MODULE}-{NAME}.arch.md
```

#### Step 5.1: 两级编号关系

当一个技术主题需要拆分为“总技术规范 + 多个子技术规范”时，保留 4 位数字编号并按两级关系组织：

| 编号段 | 含义 | 示例 |
|------|------|------|
| 前两位 | 技术主题分组 | `01xx` 表示同一主题组 |
| 后两位 | 组内技术规范 | `0100` 为分组总规范，`0101` 为子规范 |

- 仅支持两级：`GG00` 为分组总技术规范，`GG01`-`GG99` 为该分组下的子技术规范；不要继续拆成第三级。
- 创建子技术规范前，先检查对应 `GG00` 是否存在；不存在时询问用户是先创建总规范，还是将当前规范作为普通独立规范。
- 例如“命令行交互技术规范”可使用 `0100`，其子规范依次使用 `0101` 自动补全、`0102` 智能提醒、`0103` 参数格式。
- 没有父子关系时，沿用现有 4 位编号的下一个可用编号，不强行分组。
- 更新 `az-sdd/ARCH.md` 索引时，在规范名称或所属模块中保留父子关系可读信息，并填写父规范编号，便于快速识别同组规范。

### Step 6: 更新索引

更新 `az-sdd/ARCH.md` 中的项目级技术约束和技术规范列表。若创建的是项目级架构，则保留索引区并记录全局决策；若创建的是功能级规范，则追加到索引。

### Step 7: 输出结果

```
✅ 技术规范已创建！

📄 文件：az-sdd/arch/{ID}-{MODULE}-{NAME}.arch.md

🔑 关键技术决策：
1. {DECISION_1}
2. {DECISION_2}

📊 涉及软硬件组件：
- {COMPONENT_1}
- {COMPONENT_2}

💡 下一步：
1. /az-sdd-coder 按 spec + arch 开始代码实现
2. /az-sdd-tester 按 spec 的验收项和 arch 的运行条件做人工验收
```

## arch 禁止写入示例

- ❌ 用户希望页面好用
- ❌ 登录按钮必须放在右上角
- ❌ 用户名为空时提示"用户名不能为空"
- ❌ 新增"忘记密码"功能

这些属于产品行为、用户体验或验收口径，应写入 spec。arch 只能说明如何实现、如何部署、如何验证。

## 错误处理

| 情况 | 处理方式 |
|------|---------|
| az-sdd/ 不存在 | 提示先执行 /az-sdd-init |
| 对应 spec 不存在 | 提示先创建功能规范 |
| 功能较简单 | 建议跳过，仅使用 spec 中的轻量实现影响提示 |
| 许可证风险 | 必须提示用户，等待确认 |
