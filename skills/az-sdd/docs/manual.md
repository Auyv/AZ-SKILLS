# AZ-SDD v4 手动操作指南

本指南用于没有 Agent 自动编排时手工维护 AZ-SDD v4 项目，并保留 v3 兼容流程。

## v4 命令流程

1. 新项目先运行 `init ... --dry-run`，确认后追加 `--apply`；v3 项目使用 `migrate --from v3 --to v4`。
2. 使用 `change-init` 创建 change；先确认 target、operation 和 base_sha256。
3. 完成 proposal、spec.delta；复杂变更补 design。
4. 在 tasks 中维护任务，在 evidence 中保存测试和实现证据。
5. 在 acceptance 中记录人工验收，并写 `验收结果: 通过`。
6. 运行 `change-validate`；通过后先执行 `archive ... --dry-run`，确认后执行 `--apply`。

详细 delta 格式见 `../shared/references/delta-format.md`。归档失败时工具自动回滚，并返回 `.ai_tmp/bak/az-sdd-v4/` 下的备份路径。

## v3 兼容手动流程

### 1. 初始化

在项目根目录创建 `az-sdd/`，并准备：

- `INIT.md`：项目目标、技术栈、约束和运行方式；
- `STATUS.md`：当前阶段、焦点、阻塞和下一步；
- `TRACK.md`：关键事件日志；
- `SPEC.md`、`ARCH.md`、`FEEDBACK.md`：索引；
- `spec/`、`arch/`、`coding/`、`test/`、`reports/`、`feedback/`：制品目录。

### 2. 创建规范

在 `az-sdd/spec/` 创建 `{ID}-{name}.spec.md`，写明：

1. 背景与用户目标；
2. 范围与非目标；
3. 用户场景；
4. 功能需求；
5. 非功能需求；
6. 验收标准；
7. 自动化测试和人工测试项；
8. 关联技术规范。

完成审核后，把规范状态从“草稿”改为“已批准”，同步更新 `SPEC.md` 和 `STATUS.md`。

### 3. 创建技术规范

复杂功能在 `az-sdd/arch/` 创建 `{ID}-{name}.arch.md`，记录：

- 技术选型与理由；
- 模块、接口和数据模型；
- 部署、运行、启动和关闭方式；
- 硬件及外部依赖；
- 风险、回退和验证条件。

技术规范不能修改功能规范的产品验收口径。

### 4. 编码

编码前确认：

- spec 已批准；
- 风险要求的 design 已完成；
- 没有未解决的 critical 冲突；
- 开发计划中的任务能追溯到 spec。

在 `az-sdd/coding/` 创建时间戳计划，记录任务、涉及文件、测试命令、结果和遗留问题。

### 5. 自动化测试

优先使用项目已有测试入口。保存：

- 执行命令；
- 执行时间；
- 通过/失败数量；
- 失败原因；
- 对应验收标准。

测试失败时保持“开发中”或回退到“开发中”，不得直接进入待验收。

### 6. 人工验收

根据 spec 中的 MT 用例创建测试单。每项记录：

- 前置条件；
- 操作步骤；
- 预期结果；
- 实际结果；
- 通过/失败；
- 异常和证据。

全部必要用例通过后才能进入“待验收”或“已完成”。

### 7. 反馈处理

在 `az-sdd/feedback/` 创建 `FB-{YEAR}-{SEQ}.feedback.md`，记录原始描述、影响、分类、处理计划、验证方式和关闭条件。

反馈状态使用：待澄清、已计划、处理中、待验证、已解决、已关闭、待复现、转需求。

### 8. 状态维护

- `STATUS.md` 只保留当前态。
- `TRACK.md` 追加关键事件，不复制完整规范。
- `SPEC.md`、`ARCH.md`、`FEEDBACK.md` 只维护索引和链接。
- 每次状态变化都记录原因、证据和下一步。

### 9. 完成检查

功能标记完成前逐项检查：

- [ ] 规范已批准；
- [ ] 任务全部完成；
- [ ] 自动化测试通过或有合理说明；
- [ ] 必要人工验收通过；
- [ ] 未关闭反馈已处理或明确挂起；
- [ ] STATUS、索引和功能文件状态一致；
- [ ] TRACK 已记录关键事件。
