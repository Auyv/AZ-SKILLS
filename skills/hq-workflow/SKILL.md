# 鸿泉多仓库 CI 工作流

适用于一个产品配置仓库与多个 MPU 应用仓库协同变更的任务，尤其是 INI 配置迁移至 `default.prop`、平台化持续集成验证和多仓库 MR 交付。

## 先决规则

1. 完整读取全局规则 `rules/AZ_GLOBAL.rules.md`、当前工作区及各目标仓库的 `AGENTS.md`；涉及 Git 时再读取 `rules/git.rules.md`。
2. 在修改前列出“产品配置文件 → 应用仓库 → 配置加载代码 → 原目标分支”的映射，请用户确认任何会改变兼容策略、删除范围或验收方式的歧义。
3. 保留文件编码与换行。删除未跟踪配置文件前，先在 `.ai_tmp/bak/` 建立可恢复副本。

## 实施流程

### 1. 定义配置契约

- 从原 INI 提取 section、key、默认值、取值范围与实际读取位置；不要迁移没有代码消费者的无效配置。
- 按用户指定的命名规则生成属性。例如：`persist.bas.<进程名>.<section>.<key>`。
- 默认在 `default.prop` 文件末尾集中追加属性块；保留注释示例（例如可选插件数量），不要将属性穿插进原有内容。
- 除非用户为某个应用明确改写策略，保留兼容顺序：发现旧 INI 时优先读取 INI；INI 缺失时读取属性；属性不可用时使用现有默认值。

### 2. 最小化应用改造

- 仅在实际读取配置的模块中加入属性读取、参数校验和来源日志；C/C++ 类型声明必须先定义后使用，避免依赖特定编译器接受前置枚举声明。
- 如新增属性库，确认各应用 CMake 的链接依赖完整，并检查初始化与释放是否成对。
- 更新必要的应用说明、交接文档或配置示例。没有真实消费者、没有产品配置或没有兼容要求的内容不得臆造。

### 3. 静态验证

- 对每个仓库运行 `git diff --check`；若文件为 CRLF，使用 `git -c core.whitespace=cr-at-eol diff --check`。
- 核对属性数量与原有效 INI 项一一对应，检查 `default.prop` 的键名、默认值和注释示例。
- 运行可获得的目标构建或最小语法检查；记录未执行完整构建的原因。遇到 CI 编译错误时，根据日志精确修复源分支，重做最小验证后再推送。

### 4. 分支、提交与 MR

1. 每个受影响仓库从其原目标分支创建独立任务分支，名称遵循当前 Git 规则。
2. 仅提交本仓库的相关文件，推送任务分支；提交信息说明行为变更和影响范围。
3. 创建“任务分支 → 原目标分支”的 GitLab MR，描述配置来源优先级、产品影响和验证结果。
4. **禁止直接向远端目标分支推送、快进或合并。** CI 通过后只报告 MR 状态，等待人工审核、批准和合并。

当用户要求“同步”或“合并”时，默认理解为创建或更新对应 MR；如果源分支已包含额外 CI 修复，继续推送源分支，MR 会自动更新。

### 5. 持续集成验证

- 用户需在产品 manifest 中临时引用测试分支时，只替换本次涉及仓库的 `revision`，并保留其余项目引用不变。验证 XML 语法与 diff；除非用户要求，不提交该临时清单。
- 用户指定脚本或 `git_pull_xml` 时优先使用该入口，不以手工拆解命令替代。
- CI 异常应先提取首个真实编译/链接错误，区分告警与失败根因。修复后更新源分支与对应 MR，禁止以直接修改目标分支作为恢复手段。

### 6. 收尾核对

- 使用远端 `git fetch` 与 `git merge-base --is-ancestor origin/<source> origin/<target>` 检查每个 MR 是否已合入。若目标分支等于源分叉点，明确报告“尚未合入”。
- 汇总仓库、源/目标分支、提交、MR URL、CI 结果、临时 manifest 状态与待人工动作。
- 未获明确授权，不删除测试分支、恢复产品清单、合并 MR 或修改远端目标分支。

## 停止条件

在以下情况停止写入并请求用户决定：兼容优先级不明确、目标分支未知、CI 需要未授权凭据/外部审批、存在无法自动解决的冲突，或工作区含可能被覆盖的无关修改。
