# 归档前"三件套补全"实战手册

本文件是 `az-issue-tracker` SKILL.md 中"归档前的三件套补全流程"和"归档后追加内容"两节的实战补充，提供典型场景下归档前要把 01/02/03 三个文件补到何种程度的样例。

## 为什么需要这一步

`scripts/issue_tracker.py` 的 archive 子命令只做"移动目录"这一件事，不会校验内容。`create` 时三件套是模板生成、字段大多为"待补充"，阶段 1 通常只是初步登记。所以**归档前必须把内容补齐**，否则归档后目录里会残留 `<在此处填写>` 模板占位符，影响后续检索与跨项目复用。

## 场景 A：误报 / 设计预期 / 无需改软件

> 案例：HQG612 空调 CAN 报文外发异常（2026-06-29·HQG612·空调CAN报文外发异常）

### 01_问题详情.md 应有的字段

- 状态：`已解决（误报/设计预期）`
- 初步判断：明确写"误报"或"设计预期"，并解释为什么
- 影响范围：仅限问题触发的窗口 / 设备，**不夸大**；同时点明"测试用例误判"带来看似严重的工单
- 验收标准：全部打勾，因为结论已经定性

### 02_排查记录.md 追加的"阶段 N（结论）"

阶段 2 收尾的关键字段写法：

- `conclusion`：定性句子 —— "本问题定性为'误报'，非软件 BUG：MCU 设计为波特率自适应窗口期不外发空调 CAN 报文，软件逻辑无需调整；测试用例需修订..."
- `verification-result`：必须包含**三类证据** ——
  1. 两台终端日志显示所处状态
  2. 与研发 code owner 的确认记录
  3. 与测试用例负责人的用例核对记录
- `next-plan`：明确"不开发、不发版、直接归档" + 测试用例修订负责人

### 03_总结汇报.md 的 5W2H 写法

| 字段 | 误报场景下的关键写法 |
| --- | --- |
| Why（为什么） | **双重原因**：设计预期 + 测试用例误判。两个都要写明，缺一会被误读为"软件 BUG 改完就完了" |
| How（怎么发生） | 拉日志 → 比对 → 复核代码 → 对齐 code owner → 对齐测试用例，每步 1 行 |
| How Much（影响） | 软件侧 0 + 文档侧 N 条用例修订 + 工单侧关闭 |
| 解决方案·临时方案 | 通知反馈人关闭误报工单 / 当面解释清楚 |
| 解决方案·永久方案 | 测试团队修订用例剔除该窗口；列出修订后的判定条件 |
| 后续跟踪 | 跨项目检查同类用例是否含类似误判 |

完整实例：`项目集/HQG612/历史问题/2026-06-29·HQG612·空调CAN报文外发异常/03_总结汇报.md`。

## 场景 B：真 BUG → 改代码 → 回归通过

### 验收标准必须打的勾

- [ ] 问题现象不再出现（回归用例通过）
- [ ] 关键日志或截图已补充
- [ ] 相关负责人确认（含研发 code owner + 测试）
- [ ] 已发布版本号 + 升级路径已写明

### 03 总结汇报必须有的"版本号 + 升级路径"段落

不能用模糊的"已修复"收尾。要写：

- 修复版本号（commit SHA / build 号 / 灰度策略）
- 现场设备升级路径（OTA / U 盘 / 远程推送 / 召回）
- 影响设备清单（哪些 SN 需要升级、哪些已升级）

## 场景 C：挂起 / 等待外部依赖

### 状态字段

- `状态：已挂起`
- `挂起原因：等待 XX 厂商回复 / 等待硬件批次回厂`
- `预计恢复日期：YYYY-MM-DD`

### 03 总结汇报

"根本原因"留为"已定位，待外部响应"，"后续跟踪"必须写：

- 谁在跟（具体到人 / 工号）
- 下一次 sync 时间
- SLA / 客户已知会的时长

## 场景 D：单根因 + 多处本地修改

> 案例：HQT401-K01 海外路试偶现网络异常-拨号失败（2026-07-13·HQT401-K01·海外路试偶现网络异常-拨号失败）

用户反馈长这样：

> 原因：疑似设备拨号执行此处达到上限。
> 解决方案：①拨号配置 mode1 → mode2；②增加 mcu 退出 ecall 时主动清除"网络检测禁止"标志。

**关键识别**：用户列出了"一处原因 + 两处修改"，Agent 很容易自动套用"双重根因 + 两个并列方案"的框架写进文档 —— 这是错的。两处修改很可能是同一根因下的协同修复（例如：①让拨号能循环；②确保循环能力不被遗留策略抑制），而不是两条独立的处置路径。

**自检问题**（归档前必须澄清）：

1. 这是单根因还是多根因？
2. 两处修改是并列方案（每条独立解决一部分）还是同一根因下的协同修复（缺一不可 / 互相依赖）？
3. 解决的是"是什么坏了"（现象）还是"为什么会坏"（机制）？

**澄清后的正确写法**（以本案例为模板）：

### 01_问题详情.md

```markdown
## 初步判断

**根本原因**：设备没能循环执行拨号 —— 在反复唤醒 / 弱信号场景下，拨号流程不能循环重试，导致注网成功后一直没有真正发起拨号、没有 IP（`has_addr` 不为 1 是这一现象的直接表征，是正常的）。

- 模组工单答复：`has_addr` 不为 1 是正常行为（设备处于注网成功但未拨号的中间态），本机侧排查方向已收束
- 处置思路：单根因下两处本地优化（同一根因、不同位置的两个修改点），而不是两个并列方案

## 处置（单根因 + 两个本地修改点）

| # | 修改点 | 作用 |
| --- | --- | --- |
| 1 | ... 配置 mode1 → mode2 ... | 解决"拨号不能循环重试"的核心问题 |
| 2 | ... ecall 退出清除标志 ... | 确保 ecall 后第一次拨号决策窗口不会被遗留标志抑制 |
```

### 03_总结汇报.md 的 5W2H

| 字段 | 单根因场景的关键写法 |
| --- | --- |
| Why | **单根因**：设备没能循环执行拨号。两处修改都是同一根因下的协同修复 |
| 解决方案·方案说明 | 必须显式声明"不是两个并列方案，而是同一根因下的两处本地修改点" |
| 解决方案·修改点表格 | 列"# 修改点 \| 作用"，写清楚各点之间的依赖或协同关系 |
| 经验沉淀 | 加一条"`X` 是现象不是 BUG"——本次能及时止步于表层假象、避免无意义地改模组兼容判断 |

### 关键反例（不要这样写）

- ❌ 写"双重根因：①xxx ②xxx"
- ❌ 解决方案拆成"方案 1：xxx；方案 2：xxx"，并列叙述
- ❌ 经验沉淀里只提"循环拨号"或只提"ecall 退出"，不提两者的协同关系

如果两处修改的确是并列方案（每条独立解决一条独立的根因），才用双重根因叙述。**默认先按单根因追问**，别假设。

## 场景 E：归档后追加内容（补丁场景）

> 案例：HQT401-K01 海外路试偶现网络异常-拨号失败 —— 归档后移远工单 QCS-145677 给官方答复，又补了一个"阶段 4（收束）"

**典型触发**：

- 模组/平台工单在归档后给出官方答复
- 测试用例修订完毕 / 验证用例通过
- 跨项目核对结论出来，需要把适用范围 / 升级清单补全

**操作步骤**：

1. `daily --query "<关键词>"` 会返回 `ERR_ISSUE_NOT_FOUND`，**这是预期行为**，不是 bug
2. 用 `patch` 工具直接编辑归档目录下三个文件：
   - `02_排查记录.md`：文件末尾追加新阶段小节，手写标题
     ```markdown
     ---

     ## YYYY-MM-DD 阶段 N（HH:MM · 备注关键词）

     **排查目标**
     ...

     **分析过程**
     ...
     ```
     阶段号 = 现有最大阶段 + 1；时间戳用当前时间
   - `01_问题详情.md`：状态、验收标准、对外沟通小节（保持单一来源）
   - `03_总结汇报.md`：5W2H 表的 Why / 解决方案 / 经验沉淀 / 后续跟踪
3. **不要再次调用 `archive`** —— 目录已经在 `项目集/{项目}/历史问题/`，不需要再移动

**归档后追加的常见字段同步表**：

| 归档前状态 | 归档后追加（如官方答复、修订完毕） | 同步目标文件 |
| --- | --- | --- |
| 阶段 N（结论） | 阶段 N+1（收束 / 验证） | 02 |
| 状态：`已解决` | 不变；验收标准新条目打勾 | 01 |
| 对外沟通：跟踪中 | 对外沟通：已答复 / 已关闭 | 01 |
| Why：待补 | Why：单根因 + 完整机制 | 03 |
| 后续跟踪：跟踪中 | 后续跟踪：已答复归档 / 已升级 | 03 |

## 通用自检清单（归档前跑一遍）

```text
[ ] 02_排查记录.md 最后一个阶段的"conclusion"不是空
[ ] 01_问题详情.md 的"状态"字段不是"待排查"
[ ] 01_问题详情.md 的"验收标准"全部打勾（除了明确不适用项）
[ ] 03_总结汇报.md 不含 "<在此处填写>" 占位符
[ ] 03_总结汇报.md 的 Why / How / How Much 字段都非空
[ ] 03_总结汇报.md 的"后续跟踪"段落写明责任人（不是"待定"）
[ ] 多修改点问题的 03 总结汇报明确写了"是单根因 / 多根因"，不是默认双重根因
```

自检通过后再执行 archive。

## 归档后追加内容自检清单

```text
[ ] 02_排查记录.md 末尾追加了新的"## YYYY-MM-DD 阶段 N"小节
[ ] 01_问题详情.md 状态、验收标准、对外沟通三个小节都已同步
[ ] 03_总结汇报.md 的 Why / 解决方案 / 后续跟踪都已同步
[ ] 三个文件之间叙述一致（特别是"已答复 / 已升级"等带时态的状态字段）
[ ] 没有再次调用 archive（归档只做一次）
```
