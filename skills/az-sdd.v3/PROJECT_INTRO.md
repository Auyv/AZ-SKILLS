# AZ-SDD v2 — 规范驱动开发智能助手

> 让用户只需描述业务，AI 自动完成从需求规范到代码测试的全流程。

---

## 一、项目概述

**AZ-SDD** 是一套基于 **SDD（Spec-Driven Development，规范驱动开发）** 理论的 AI 开发辅助系统。以 **8 个模块化 SKILL** 的形式运行在 AI 编程助手（Cline / Claude Code）中，将传统软件开发流程自动化、智能化。

### 核心价值

| 传统开发 | AZ-SDD |
|---------|--------|
| 非技术人员难以参与 | 只需描述业务需求，无需技术背景 |
| 需求传递失真 | AI 自动提取技术约束，规范即代码蓝图 |
| 流程碎片化 | 8 个 SKILL 覆盖完整生命周期 |
| 测试验收割裂 | test + confirm 合并为一体化验收 |
| 状态不同步 | 规范文件为唯一真实来源，自动追踪 |
| 流程无监控 | az-sdd-rules 规则守卫自动监控 |

## 二、核心技术特性

### 2.1 双向约束提取

系统能够从非结构化的业务描述中，自动识别并提取技术要素：

```
用户输入：我想做个任务管理，用户可以创建任务、设置截止日期

AI 自动提取：
├── 数据存储：任务需要持久化 → JSON 文件存储
├── 认证需求：需要登录吗？ → 询问用户确认
├── 字段定义：任务包含标题、描述、截止日期、状态
└── 关联关系：任务属于某个用户
```

### 2.2 状态机驱动的生命周期管理

9 个状态组成完整生命周期，状态即规范，规范即代码：

```
草稿 → 审核中 → 已批准 → 开发中 → 测试中 → 待验收 → 已完成 → 已发布
         ↓
     （可回退）
```

**关键设计**：规范文件本身是状态的唯一真实来源，任何查询都追溯规范文件。

### 2.3 批量智能处理

- **批量规范创建**：一次描述多个功能，AI 自动拆分逐一确认
- **批量开发**：自动分析功能间依赖关系，生成前趋图，按批次执行
- **最小交互原则**：全程仅与用户交流 1-3 次，除非有矛盾或不清楚的问题

### 2.4 交互式 HTML 验收

测试阶段生成可交互的 HTML 页面：
- 自动检索规范文件中的测试用例（MT001, MT002...）
- 用户逐一点击验证，勾选完成
- 填写签名确认，AI 自动更新状态 + 生成 CHANGELOG

### 2.5 面向用户的反馈系统

```
用户反馈 → AI 自动分类
           ├── 🐛 Bug         → 自动触发修复
           ├── 💡 改进建议     → 解释原设计，确认是否变更
           └── ✨ 新功能需求   → 自动创建新规范
```

用户无需了解内部规范，所有处理对用户透明。

### 2.6 规则守卫机制

az-sdd-rules SKILL 作为规则守卫，**自动加载**监控整个开发流程：
- 确保 SKILL 按正确顺序执行
- 确保状态变更符合转换规则
- 发现偏离时及时介入纠正
- 提供规则解释和查询

## 三、系统架构

### 3.1 SKILL 体系（8个）

| SKILL | 命令 | 阶段 | 说明 |
|-------|------|------|------|
| az-sdd-init | `/az-sdd-init` | 项目初始化 | 创建 az-sdd 档案目录结构 |
| az-sdd-spec | `/az-sdd-spec` | 功能规范 | 编写功能规范（含 AI 提取的技术约束） |
| az-sdd-arch | `/az-sdd-arch` | 技术规范（可选） | 为复杂技术决策创建独立文档 |
| az-sdd-coding | `/az-sdd-coding` | 代码实现 | 按照规范实现功能代码 |
| az-sdd-test | `/az-sdd-test` | 测试验收 | 自动化测试 + 人工测试 + 用户确认 + 状态更新 |
| az-sdd-track | `/az-sdd-track` | 状态追踪 | 管理项目工作状态 |
| az-sdd-feedback | `/az-sdd-feedback` | 用户反馈 | Bug / 改进建议 / 新功能需求 |
| **az-sdd-rules** | `/az-sdd-rules` | 规则守卫 | **自动加载**，监控流程，发现偏离时介入 |

## 四、创新点

### 4.1 零门槛需求表达

传统开发要求用户具备技术理解能力。AZ-SDD 让用户**只需描述业务**，AI 自动完成：
- 从自然语言提取功能点
- 识别技术约束（存储、认证、接口等）
- 生成结构化规范文档

### 4.2 规范即代码蓝图

规范文件不是孤立的文档，而是**贯穿开发全流程的核心**：
- 编码前：检查规范后才动手
- 测试时：从规范读取测试用例
- 验收时：规范状态驱动整体状态

### 4.3 状态驱动的自动化

状态变更有明确的触发条件和执行 SKILL：
- `开发中 → 测试中`：自动化测试全部通过后自动触发
- `测试中 → 待验收`：测试报告生成后自动更新
- `待验收 → 已完成`：用户签名确认后自动更新

### 4.4 批量开发的前趋图

系统能够自动分析功能间的依赖关系，生成可视化的前趋图：

```
     [0001-登录]
          │
          ▼
     [0002-任务创建] ← ─ ─ ─ ┐
          │                  │
          ▼                  │
     [0003-任务列表]          │
          │                  │
          ▼                  │
     [0004-任务统计] ─ ─ ─ ─ ─┘
```

### 4.5 HTML 交互式验收

测试阶段生成独立的 HTML 页面：
- 主题色区分（Coding 报告绿色 / Test 报告蓝色）
- 点击标题用 VSCode 打开规范文件
- localStorage 保存验收状态，无需服务器

### 4.6 规则守卫机制

az-sdd-rules 作为独立的守卫 SKILL：
- **自动加载**：触发任何 az-sdd-* SKILL 时自动介入
- **流程监控**：确保 SKILL 按正确顺序执行
- **状态校验**：确保状态变更符合转换规则
- **干预纠正**：发现偏离时及时介入，支持强制绕过

## 五、技术实现

### 5.1 技术栈

| 组件 | 技术 |
|------|------|
| AI 助手 | Claude (Cline) / Claude Code |
| 规范格式 | Markdown |
| 状态存储 | JSON + Markdown 文件 |
| 交互界面 | HTML + localStorage |
| 脚本工具 | Python |
| 规则配置 | YAML |

### 5.2 CLI-First 设计

除界面交互外，所有功能都支持命令行：

```bash
/az-sdd-init      # 初始化项目
/az-sdd-spec       # 创建功能规范
/az-sdd-arch       # 创建技术规范（可选）
/az-sdd-coding     # 代码实现
/az-sdd-test       # 测试验收
/az-sdd-track      # 状态追踪
/az-sdd-feedback   # 用户反馈
/az-sdd-rules      # 规则守卫（自动加载）
```

### 5.3 模板系统

每个 SKILL 都配备了标准模板：
- `spec.template.md` — 功能规范模板
- `arch.template.md` — 技术规范模板
- `test-report.template.md` — 测试报告模板
- `operation-manual.template.md` — 操作手册模板

## 六、与传统开发流程对比

| 维度 | 传统开发 | AZ-SDD |
|------|---------|--------|
| 需求获取 | 需求文档 → 技术方案 → 代码 | 业务描述 → AI 提取 → 规范 → 代码 |
| 角色分工 | 产品经理 + 开发者 + 测试工程师 | 非技术人员 + AI 助手 |
| 技术约束 | 开发者自行判断 | AI 自动识别并确认 |
| 测试验收 | 测试报告 + 确认签字两次交互 | 一次完成，HTML 交互 |
| 状态管理 | 分散在多个工具 | 规范文件为唯一来源 |
| 流程监控 | 依赖人工或外部工具 | az-sdd-rules 自动监控 |
| 反馈处理 | 手动分配任务 | AI 自动分类触发 |
| 学习成本 | 需要了解整个开发体系 | 只需描述业务 |

## 七、适用场景

### 7.1 适用场景

- **个人项目 / 小团队**：快速从想法到可运行代码
- **非技术产品经理**：独立完成功能规范到验收的全流程
- **AI 编程助手集成**：作为 Claude Code / Cline 的技能扩展
- **教学辅助**：帮助学生理解软件开发流程

### 7.2 不适用场景

- 已有成熟开发流程和团队分工的大型项目
- 需要实时多人协作的开发环境
- 对安全性要求极高的系统
