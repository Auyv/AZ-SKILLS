# AZ-SDD-SPEC

功能规范编写 - 将业务需求转化为规范文档，支持单功能和批量处理。

## 两种处理模式

```
┌─────────────────────────────────────────────────────┐
│                    批量模式                          │
│  用户一次性发送多个需求 → AI 拆分 → 逐个确认 → 批量生成  │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│                    单个模式                          │
│  用户发送一个需求 → AI 分析 → 提取技术约束 → 生成规范  │
└─────────────────────────────────────────────────────┘
```

## 执行步骤

### Step 0: 判断处理模式

```
1. 检查用户输入中是否包含多个功能需求
   → 多个功能（用自然语言描述、编号、换行等方式分隔）
      → 进入【批量模式】

   → 单个功能
      → 进入【单个模式】
```

**识别多功能的信号**：
- 用了编号列表（1. 2. 3. 或 需求一、需求二）
- 用了"和"、"以及"、"还有"
- 用换行分隔多个功能描述
- 直接说"我有这几个需求"、"帮我规划"

### Step 1: 批量模式 - AI 自动拆分

#### Step 1.1: 识别并列出所有功能

```
📋 我识别到以下 [N] 个功能需求，请确认拆分是否正确：

  [1] {功能A名称}
      简述：{一句话描述}

  [2] {功能B名称}
      简述：{一句话描述}

  [3] {功能C名称}
      简述：{一句话描述}

  ──────────────────────────────
  
  ✅ 拆分正确，开始逐个编写
  ✏️ 需要调整（告诉我如何修改）
```

#### Step 1.2: 询问拆分确认

```
请选择：
1. ✅ 拆分正确，开始逐个编写
2. ✏️ 需要调整（请说明如何修改）
3. ❌ 取消，暂不生成
```

### Step 2: 单个模式 - 检查环境

```
1. 检查 az-sdd/ 目录是否存在
   → 不存在：提示用户先执行 /az-sdd-init
   → 存在：继续
2. 读取 .config/naming.yaml 获取编号规则
3. 读取 SPEC.md 获取现有功能列表
```

### Step 3: 确定功能编号

**如果有参数**（用户指定了编号如 "0001"）：
```
→ 使用用户指定的编号
→ 检查编号是否已存在
  → 已存在：询问是"覆盖"还是"更新"
```

**如果没有参数**：
```
→ 读取 SPEC.md 获取下一个可用编号
→ 自动递增
```

### Step 4: 收集业务信息

**必须询问用户**（用通俗易懂的语言）：

1. **功能名称** - 这个功能叫什么？（如：用户登录、任务统计）
2. **功能描述** - 这个功能是做什么的？（用一句话描述）
3. **使用场景** - 用户在什么情况下会用这个功能？
4. **核心步骤** - 用户使用这个功能的主要流程是什么？（1、2、3...）
5. **输入项** - 用户需要提供什么信息？
6. **输出项** - 功能执行后，用户能看到什么结果？
7. **特殊情况** - 有什么需要特别注意的情况吗？（如：空数据、错误提示）

> ⚠️ **重要**：使用通俗语言，不要说"接口"、"数据库"、"API"等术语。

### Step 5: AI 自动分析 - 提取技术约束

分析用户提供的业务信息，自动提取技术要素：

```
📋 已识别以下技术约束，请确认：

| 约束类型 | 识别内容 | 确认 |
|---------|---------|------|
| 数据存储 | 需要保存用户输入的数据 | ⬜ |
| 身份验证 | 需要识别用户身份 | ⬜ |
| 外部接口 | 需要调用XX服务 | ⬜ |
| 文件操作 | 需要导出/导入文件 | ⬜ |

💡 如有遗漏，请补充；如有不准确，请纠正。
```

**AI 自动识别的技术约束类型**：

| 类型 | 识别信号 | 询问确认 |
|------|---------|---------|
| 数据存储 | 需要"保存"、"记录"、"存储" | 用什么存？文件？数据库？ |
| 用户认证 | 需要"登录"、"验证"、"权限" | 如何验证用户？ |
| 外部调用 | 需要"调用"、"对接"、"集成" | 调用什么服务？ |
| 文件操作 | 需要"导出"、"导入"、"上传" | 文件格式？大小限制？ |
| 实时处理 | 需要"即时"、"实时"、"推送" | 对响应时间有要求吗？ |
| 批量处理 | 需要"批量"、"大量"、"定时" | 数据量级？执行频率？ |

### Step 6: 生成规范文档

按照模板生成规范文件，包含两部分：

```
az-sdd/spec/{ID}-{MODULE}-{NAME}.spec.md
```

**Part 1: 业务部分**（用户可见，用户填写）
**Part 2: 技术约束**（AI 生成，用户确认）

### Step 7: 询问是否需要独立技术规范

```
📝 技术规范选项：

1. 【推荐】简单模式：技术约束直接写在功能规范里

   - 输出：只需维护一个文件

2. 独立模式：为复杂技术决策创建单独的技术规范

   - 输出：功能规范 + 技术规范文件
   - 可后续使用 /az-sdd-arch 补充

请选择：1 或 2
```

### Step 8.1: 生成规范总览页面

### AI 响应示例

```
📋 我识别到以下 [5] 个功能需求，请确认拆分是否正确：

  [1] 用户注册
      简述：用户可以创建新账号

  [2] 用户登录

  [3] 任务列表
```

## 验收标准格式

必须使用可测试的验收标准，**同时在规范中生成 MT 格式的测试用例**：

### 1. 验收标准（[001] 格式 - 用于 AI 自动测试）

```markdown
## 验收标准

- [ ] [001] 用户可在 XXX 界面访问此功能
- [ ] [002] 输入 A 时，系统返回 B
- [ ] [003] 条件 C 满足时，执行 D
- [ ] [004] 出现错误 E 时，显示 F 提示
```

### 2. 测试用例（MT001 格式 - 用于人工测试验收）

**重要**：coding 阶段会自动将验收标准转换为 MT 格式测试用例，包含测试步骤和预期结果。

```markdown
## 测试用例

### MT001 界面布局验证
- **测试步骤**：1. 打开登录页面 2. 检查界面元素
- **预期结果**：页面正常显示所有元素
- **验收标准**：[001]

### MT002 错误提示验证
- **测试步骤**：1. 输入空用户名 2. 点击登录
- **预期结果**：显示红色错误提示"用户名不能为空"
- **验收标准**：[004]
```

**⚠️ 注意**：
- `[001]` 验收标准由 AI 自动生成，用于自动化测试
- `MT001` 测试用例由 AI 根据验收标准转换生成，用于人工测试验收
- 测试用例必须写入规范文件，test 阶段会从规范文件读取

**禁止**：
- ❌ "功能应该好用" （不可测试）
- ❌ "界面要美观" （主观判断）
- ❌ "性能要快" （未定义标准）

**允许**：
- ✅ "点击按钮后 1 秒内显示结果"
- ✅ "列表正确显示所有任务"
- ✅ "错误时显示红色提示"
- ✅ "用户名为空时，禁止提交并显示提示"
