# AZ-SDD-SPEC

功能规范编写 - 将业务需求转化为面向产品用户、验收者和需求确认的功能契约，支持单功能和批量处理。

## 职责边界

| 问题 | spec 回答 | arch 回答 |
|------|-----------|-----------|
| 给谁用 | 产品用户、业务负责人、验收者 | 研发人员、测试人员、后续 AI 实现流程 |
| 关注什么 | 做什么、谁使用、怎么操作、如何验收 | 怎么实现、怎么部署、怎么验证、依赖什么软硬件 |
| 主要产物 | 用户目标、使用场景、输入输出、验收标准、人工测试用例 | 技术选型、模块边界、API、数据模型、部署/运行环境 |
| 禁止写什么 | 技术选型、接口设计、数据库表结构、部署架构 | 新增产品需求、改变验收口径、替用户决定功能行为 |

> 冲突处理：当 spec 与 arch 冲突时，不能默认用 arch 覆盖 spec。spec 是用户价值契约，arch 是实现契约；实现方案必须服务 spec。若确需调整产品行为或验收标准，先回到 spec 修改并重新审核。

## 日常使用边界

- 仅在用户显式调用 `/az-sdd-spec`、`az-sdd spec`、`sdd spec`，或明确进入 AZ-SDD/SDD 流程时创建或修改规范。
- 默认使用 `standard` 模式；小改动可用 `lite`，复杂交付功能可用 `strict`。
- 如果用户只是讨论需求或产品方案，不要直接生成档案；只有用户显式要求进入 AZ-SDD/SDD 后才写入 `az-sdd/spec/`。
- 执行前检查 `az-sdd/` 是否存在；不存在时提示先运行 `/az-sdd-init`。

## 两种处理模式

```
┌─────────────────────────────────────────────────────┐
│                    批量模式                          │
│  用户一次性发送多个需求 → AI 拆分 → 逐个确认 → 批量生成  │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│                    单个模式                          │
│  用户发送一个需求 → AI 分析 → 提取功能契约 → 生成规范  │
└─────────────────────────────────────────────────────┘
```

## 执行步骤

### Step 0: 判断处理模式

```
1. 检查用户输入中是否包含多个功能需求
   → 多个功能（用自然语言描述、编号、换行等方式分隔）
      → 进入【批量模式】

   → 单个功能
      → 进入【单个模式】
```

**识别多功能的信号**：
- 用了编号列表（1. 2. 3. 或 需求一、需求二）
- 用了"和"、"以及"、"还有"
- 用换行分隔多个功能描述
- 直接说"我有这几个需求"、"帮我规划"

### Step 1: 批量模式 - AI 自动拆分

#### Step 1.1: 识别并列出所有功能

```
📋 我识别到以下 [N] 个功能需求，请确认拆分是否正确：

  [1] {功能A名称}
      简述：{一句话描述}

  [2] {功能B名称}
      简述：{一句话描述}

  [3] {功能C名称}
      简述：{一句话描述}

  ──────────────────────────────
  
  ✅ 拆分正确，开始逐个编写
  ✏️ 需要调整（告诉我如何修改）
```

#### Step 1.2: 询问拆分确认

```
请选择：
1. ✅ 拆分正确，开始逐个编写
2. ✏️ 需要调整（请说明如何修改）
3. ❌ 取消，暂不生成
```

#### Step 1.3: 技术规范衔接（批量模式专属）

在生成规范前，只确认是否存在会影响功能拆分和验收的项目级约束；不要在 spec 流程中完成技术选型或架构设计。

---

##### Step 1.3.1: 收集项目约束

```
📐 项目约束确认

在开始生成规范前，我需要确认是否有会影响功能范围和验收方式的约束。

请提供以下信息（如果没有，可以写"暂无"）：

1. 【用户环境】
   - 用户在什么设备或系统上使用？例如 Windows 电脑、Web 浏览器、嵌入式设备。
   - 是否有必须支持的硬件、网络或离线环境？

2. 【非功能需求】
   - 响应时间、数据规模、并发人数、可靠性有没有可验收标准？
   - 有没有安全、权限、审计或数据保留要求？

3. 【外部依赖】
   - 是否必须对接已有系统、设备、文件格式或第三方服务？

4. 【是否需要技术规范】
   - 如果涉及技术选型、模块/API、数据模型、部署或硬件架构，后续使用 `/az-sdd-arch` 创建技术规范。

───────────────────────────────────

💡 spec 阶段只记录用户可感知的约束和对 arch 的引用，不在这里决定技术方案。
```

##### Step 1.3.2: 判断是否需要 arch

```
📋 技术规范建议：

基于当前需求，是否需要单独创建 arch？

- 如果只是单一功能、无新增技术决策：spec 中保留轻量实现影响提示即可
- 如果涉及多模块、软硬件环境、技术选型、API、数据模型、部署方式：建议后续执行 `/az-sdd-arch`

本次判断：{ARCH_SUGGESTION}
```

---

##### Step 1.3.3: 记录关联关系

```
如已有项目级或功能级技术规范，在 spec 中记录引用：

## 关联技术规范

- 项目级架构：az-sdd/ARCH.md（如存在）
- 功能级技术规范：az-sdd/arch/{ARCH_ID}-{NAME}.arch.md（如存在）
- 状态：待补充 / 已关联 / 不需要
```

#### Step 1.4: 逐个执行规范编写

对每个识别出的功能，依次执行【单个模式】的 Step 2-8。
**注意**：spec 中不得写入技术选型、API、数据模型或部署架构；如已有 arch，只在“关联技术规范”中引用。

4. 审核完成后：

### Step 2: 单个模式 - 检查环境

```
1. 检查 az-sdd/ 目录是否存在
   → 不存在：提示用户先执行 /az-sdd-init
   → 存在：继续
2. 读取 .config/naming.yaml 获取编号规则
3. 读取 SPEC.md 获取现有功能列表
```

### Step 3: 确定功能编号

**如果有参数**（用户指定了编号如 "0001"）：
```
→ 使用用户指定的编号
→ 检查编号是否已存在
  → 已存在：询问是"覆盖"还是"更新"
```

**如果没有参数**：
```
→ 读取 SPEC.md 获取下一个可用编号
→ 自动递增
```

### Step 4: 收集业务信息

**必须询问用户**（用通俗易懂的语言）：

1. **功能名称** - 这个功能叫什么？（如：用户登录、任务统计）
2. **功能描述** - 这个功能是做什么的？（用一句话描述）
3. **使用场景** - 用户在什么情况下会用这个功能？
4. **核心步骤** - 用户使用这个功能的主要流程是什么？（1、2、3...）
5. **输入项** - 用户需要提供什么信息？
6. **输出项** - 功能执行后，用户能看到什么结果？
7. **特殊情况** - 有什么需要特别注意的情况吗？（如：空数据、错误提示）

> ⚠️ **重要**：使用通俗语言，不要说"接口"、"数据库"、"API"等术语。

### Step 5: AI 自动分析 - 提取非功能需求与实现影响

分析用户提供的业务信息，自动提取用户可感知、可验收的非功能需求和实现影响提示：

```
📋 已识别以下非功能需求与实现影响，请确认：

| 类型 | 识别内容 | 确认 |
|---------|---------|------|
| 数据保留 | 用户希望历史记录可长期查看 | ⬜ |
| 权限行为 | 只有登录用户可访问此功能 | ⬜ |
| 外部依赖 | 用户需要对接 XX 系统或设备 | ⬜ |
| 文件要求 | 用户需要导入/导出指定格式文件 | ⬜ |
| 性能目标 | 点击后 1 秒内显示结果 | ⬜ |

💡 如有遗漏，请补充；如有不准确，请纠正。
```

**AI 自动识别的实现影响类型**：

| 类型 | 识别信号 | 询问确认 |
|------|---------|---------|
| 数据保留 | 需要"保存"、"记录"、"历史" | 保存多久？用户如何查看？ |
| 权限行为 | 需要"登录"、"验证"、"权限" | 谁可以访问？无权限时用户看到什么？ |
| 外部依赖 | 需要"调用"、"对接"、"集成" | 对接对象名称是什么？失败时用户看到什么？ |
| 文件操作 | 需要"导出"、"导入"、"上传" | 文件格式、大小、错误提示是什么？ |
| 响应体验 | 需要"即时"、"实时"、"推送" | 用户可接受的等待时间是多少？ |
| 批量处理 | 需要"批量"、"大量"、"定时" | 用户一次处理多少数据？多久完成可接受？ |

> 禁止在本步骤决定“用什么数据库/框架/API”。这些属于 arch。

### Step 6: 生成规范文档

按照模板生成规范文件，包含产品视角内容：

```
az-sdd/spec/{ID}-{MODULE}-{NAME}.spec.md
```

**Part 1: 功能契约**（用户目标、使用场景、流程、输入输出）
**Part 2: 验收契约**（验收标准、MT 人工测试用例）
**Part 3: 实现影响提示**（非功能需求、外部依赖名称、关联 arch）

### Step 7: 询问是否需要独立技术规范

```
📝 技术规范选项：

1. 【推荐】简单模式：只在功能规范里保留轻量实现影响提示
   - 适用于：单一功能、无复杂技术决策
   - 输出：只需维护一个文件

2. 独立模式：为复杂技术决策创建单独的技术规范
   - 适用于：涉及多个模块、软硬件架构、API、数据模型、部署、新技术引入
   - 输出：功能规范 + 技术规范文件
   - 可后续使用 /az-sdd-arch 补充

请选择：1 或 2
```

## 验收标准格式

必须使用可测试的验收标准，**同时在规范中生成 MT 格式的测试用例**：

### 1. 验收标准（[001] 格式 - 用于 AI 自动测试）

```markdown
## 验收标准

- [ ] [001] 用户可在 XXX 界面访问此功能
- [ ] [002] 输入 A 时，系统返回 B
- [ ] [003] 条件 C 满足时，执行 D
- [ ] [004] 出现错误 E 时，显示 F 提示
```

### 2. 测试用例（MT001 格式 - 用于人工测试验收）

**重要**：coding 阶段会自动将验收标准转换为 MT 格式测试用例，包含测试步骤和预期结果。

```markdown
## 测试用例

### MT001 界面布局验证
- **测试步骤**：1. 打开登录页面 2. 检查界面元素
- **预期结果**：页面正常显示所有元素
- **验收标准**：[001]

### MT002 错误提示验证
- **测试步骤**：1. 输入空用户名 2. 点击登录
- **预期结果**：显示红色错误提示"用户名不能为空"
- **验收标准**：[004]
```

**⚠️ 注意**：
- `[001]` 验收标准由 AI 自动生成，用于自动化测试
- `MT001` 测试用例由 AI 根据验收标准转换生成，用于人工测试验收
- 测试用例必须写入规范文件，test 阶段会从规范文件读取

**禁止**：
- ❌ "功能应该好用" （不可测试）
- ❌ "界面要美观" （主观判断）
- ❌ "性能要快" （未定义标准）

**允许**：
- ✅ "点击按钮后 1 秒内显示结果"
- ✅ "列表正确显示所有任务"
- ✅ "错误时显示红色提示"
- ✅ "用户名为空时，禁止提交并显示提示"

## 非功能需求与实现影响提示模板

```markdown
## 非功能需求

| 类型 | 用户可感知要求 | 验收方式 |
|------|---------------|----------|
| 响应时间 | 点击查询后 1 秒内显示结果 | 人工或自动计时验证 |
| 数据保留 | 历史记录至少可查询 1 年 | 构造历史数据验证 |

## 实现影响提示

| 类型 | 说明 |
|------|------|
| 权限 | 仅登录用户可使用；未登录时提示先登录 |
| 外部依赖 | 需要对接短信服务；失败时提示稍后重试 |
| 文件 | 支持导入 CSV；格式错误时显示错误行号 |

## 关联技术规范

- 项目级架构：az-sdd/ARCH.md（如存在）
- 功能级技术规范：az-sdd/arch/{ARCH_ID}-{NAME}.arch.md（如存在）
- arch 状态：不需要 / 待补充 / 已关联
```

### spec 禁止写入示例

- ❌ 后端使用 FastAPI
- ❌ 数据库表 `user(id, name, password_hash)`
- ❌ 接口 `POST /api/login`
- ❌ 使用 Redis 缓存 1 小时

这些内容应写入 arch。

## 错误处理

| 情况 | 处理方式 |
