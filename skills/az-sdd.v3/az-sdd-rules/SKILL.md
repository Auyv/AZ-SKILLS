# AZ-SDD-RULES

SDD 规范守卫 - 保护开发流程不走偏。

> 现实约束：不同 AI 平台未必支持一个 SKILL 自动拦截另一个 SKILL。
> 日常使用时优先通过 `/az-sdd-next` 进入流程；直接调用某个 az-sdd-* SKILL 时，
> 该 SKILL 必须先执行本规则的前置检查清单，再继续具体任务。

## 核心职责

```
┌─────────────────────────────────────────────────────────────┐
│                    az-sdd-rules 职责                        │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 加载规则 - 启动时加载规则配置到记忆                       │
│  2. 监控流程 - 确保 SKILL 按正确顺序执行                      │
│  3. 状态校验 - 确保状态变更符合转换规则                       │
│  4. 干预纠正 - 发现偏离时及时介入                             │
│  5. 解释规则 - 应要求解释规则含义                             │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

---

## 规则配置路径

```
az-sdd-rules/
├── SDD规则.md                   # 规则索引文档
└── az-sdd-rules-config/         # 机器可读配置
    ├── flow.yaml                # 流程定义
    ├── naming.yaml              # 命名规范
    └── states.yaml              # 状态定义
```

**注意**：本 SKILL 假设规则配置位于项目根目录的 `az-sdd-rules/` 子目录。如果路径不同，请根据实际情况调整。

## 一、必须记忆的规则

### 1.1 状态定义（9个）

| 状态 ID | 中文名称 | 图标 | 颜色 |
|---------|---------|------|------|
| draft | 草稿 | 📋 | gray |
| reviewing | 审核中 | 👁️ | yellow |
| approved | 已批准 | ✅ | green |
| developing | 开发中 | 🔨 | blue |
| testing | 测试中 | 🧪 | orange |
| acceptance | 待验收 | 🎯 | purple |
| completed | 已完成 | ✅ | green |
| released | 已发布 | 🚀 | green |
| blocked | 阻塞 | 🚧 | red |

### 1.2 状态分组

| 分组 | 包含状态 |
|------|---------|
| 进行中 | reviewing、developing、testing、acceptance |
| 已完成 | completed、released |
| 异常 | blocked |

### 1.3 正向流程

```
草稿 → 审核中 → 已批准 → 开发中 → 测试中 → 待验收 → 已完成 → 已发布
```

### 1.4 回退规则

| 当前状态 | 可回退到 | 触发条件 |
|---------|---------|---------|
| 审核中 | 草稿 | 审核拒绝，需修改 |
| 测试中 | 开发中 | 测试失败，需返工 |
| 待验收 | 开发中 | 验收不通过，需返工 |

### 1.5 SKILL 流程顺序

```
init → spec → arch(可选) → coding → test → track → feedback
```

| 顺序 | SKILL | 可跳过 |
|------|-------|--------|
| 1 | az-sdd-init | ❌ |
| 2 | az-sdd-spec | ❌ |
| 3 | az-sdd-arch | ✅（简单功能） |
| 4 | az-sdd-coding | ❌ |
| 5 | az-sdd-test | ❌ |
| 6 | az-sdd-track | ❌ |
| 7 | az-sdd-feedback | ❌（可选） |

### 1.6 跳过规则

| 跳过条件 | 可跳过项 |
|---------|---------|
| 功能非常简单明确，无需详细规范 | spec → coding |
| 用户明确说'不需要写规范，直接做' | spec → coding |
| 不涉及技术方案变更、不涉及新的技术依赖 | arch |
| 功能简单，无复杂技术决策 | arch |
| 用户选择简单模式 | arch |

## 二、自动介入时机

### 2.1 必须介入的情况

| 场景 | 偏离行为 | 介入方式 |
|------|---------|---------|
| 跳过 spec 直接 coding | spec → coding 未满足条件 | 询问是否需要创建规范 |
| 跳过 arch 但应该创建 | 功能涉及多模块/架构变更 | 建议使用 az-sdd-arch |
| 状态跳跃 | 未按顺序经历状态 | 提示正确的状态顺序 |
| 回退未记录 | acceptance → developing | 要求在 track.md 记录原因 |
| 审核未通过继续开发 | reviewing → developing | 提示必须审核通过 |
| 测试未完成提前验收 | testing → acceptance | 提示等待测试完成 |

### 2.2 可选介入的情况

| 场景 | 介入方式 |
|------|---------|
| 用户询问规则含义 | 提供规则解释 |
| 用户请求查看状态 | 显示当前状态 |
| 用户请求查看流程 | 显示流程图 |

#### 各 SKILL 执行所需的前置状态

| SKILL | 所需规范状态 | 前置动作 |
|-------|-------------|---------|
| az-sdd-coding | 必须为 `已批准` ✅ | 需先完成审核流程 |
| az-sdd-test | 必须为 `待验收` 🎯 | 需先完成开发+自动化测试 |
| 需求变更 | 无限制 | 直接执行 |

**重要**：状态必须是 `已批准` 才能开始 coding，`待验收` 才能开始验收测试。

### 3.2 发现偏离时的处理

```
检测到偏离
     │
     ▼
┌─────────────┐
│ 是严重偏离？ │   ← 检查是否违反强制规则
└──────┬──────┘
       │
  ┌────┴────┐
  │         │
  ▼         ▼
  是        否
  │         │
  ▼         ▼
  阻止      警告
  并询问    并解释
```

### 3.3 强制规则（不可违背）

1. **规范先行**：coding 前必须先有 spec
2. **状态校验**：coding 前 spec 状态必须为"已批准"，test 前必须为"待验收"
3. **状态不可跳跃**：必须按顺序经历每个状态（arch 可跳过）
4. **审核后才能开发**：spec 状态必须为"已批准"才能进入开发
5. **测试后才能验收**：spec 状态必须为"待验收"才能进入人工验收

### 3.4 警告规则（可选择忽略）

1. **arch 可跳过但建议**：功能涉及多模块时建议创建
2. **回退需记录原因**：测试/验收失败回退时需记录

- [ ] 代码已实现

## 五、介入示例

### 5.1 场景：用户明确要求在 AZ-SDD 中跳过 spec 直接 coding

```
用户：按 AZ-SDD 直接开始写代码吧，不需要规范了

AI（az-sdd-rules）：
  ⚠️ 检测到偏离 SDD 流程

  当前情况：尚未创建功能规范
  规则要求：az-sdd-spec → az-sdd-coding

  强制规则：coding 前必须先有已批准的规范
  原因：规范是代码的唯一真实来源，状态驱动的基础

  请选择：
  1. 创建功能规范（使用 /az-sdd-spec）
  2. 使用快速流程（功能足够简单时）
  3. 强制继续（了解风险，但仍要继续）

  提示：如果功能确实非常简单，可以说"功能很简单，直接做"，系统会判断是否允许跳过。
```

### 5.2 场景：状态跳跃

```
用户：我想把 spec 状态从"草稿"直接改成"已完成"

AI（az-sdd-rules）：
  ⚠️ 检测到非法状态跳跃

  当前状态：草稿
  目标状态：已完成
  正确路径：草稿 → 审核中 → 已批准 → 开发中 → 测试中 → 待验收 → 已完成

  规则：状态不可跳跃，必须按顺序经历每个状态

  请选择：
  1. 按正确流程逐步推进
  2. 查看当前 spec 状态
```

### 5.3 场景：功能复杂但跳过 arch

```
用户：开始开发这个功能吧

AI（az-sdd-rules）：
  ℹ️ 建议检查是否需要技术规范

  检测到功能涉及：
  - 多个模块（用户、任务、统计）
  - 数据存储方案
  - API 接口设计

  规则建议：复杂功能建议使用 az-sdd-arch 创建独立技术规范

  请选择：
  1. 创建技术规范（使用 /az-sdd-arch）
  2. 简单模式继续（技术约束写在 spec 中）
  3. 忽略此建议
```

### 5.4 场景：回退未记录原因

```
用户：测试失败了，返回开发状态

AI（az-sdd-rules）：
  ⚠️ 状态回退需要记录原因

  变更：测试中 → 开发中
  规则：回退时必须在 track.md 中记录原因

  请描述回退原因：
  （用户输入原因）

  已记录：
  - 日期：{DATE}
  - 变更：测试中 → 开发中
  - 原因：{用户输入}

  正在更新 track.md...
```

## 七、与其他 SKILL 的协作

```
az-sdd-rules 作为规则清单 SKILL，在其他 SKILL 执行前提供显式校验

┌──────────────┐     读取规则      ┌──────────────┐
│ az-sdd-rules │ ←────────────── │ 其他 SKILL   │
│  (规则清单)   │                 │   (执行)     │
└──────┬───────┘                 └──────┬───────┘
       │                                 │
       │  ←───── 前置检查 ────────────→  │
       │                                 │
       │  ←───── 提供规则解释 ────────→  │
       │                                 │
       │  ←───── 校验执行结果 ────────→  │
       │                                 │
```

**工作模式**：
1. 推荐从 `/az-sdd-next` 进入，由它读取状态并提示下一步。
2. 直接触发任何 az-sdd-* SKILL 时，当前 SKILL 必须先执行前置检查。
3. 需要解释状态、流程或纠偏原因时，调用 `/az-sdd-rules`。
4. 完成后验证状态更新和索引同步。

## 九、紧急绕过

在极少数情况下，用户可能需要临时绕过规则：

```
紧急绕过选项：
1. 强制继续 - 输入"FORCE"确认风险后继续
2. 跳过本次检查 - 仅本次有效
3. 禁用守卫 - 整个会话禁用 az-sdd-rules（慎用）

⚠️ 警告：绕过规则可能导致状态不一致、流程混乱
```
