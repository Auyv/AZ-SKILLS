# AZ-SDD-CODER

代码实现 - 按照规范实现功能代码，遵循 TDD + 可验证优先原则。

## 日常使用边界

- 仅在用户显式调用 `/az-sdd-coder`、`az-sdd coder`、`sdd coder`，或明确要求按 AZ-SDD/SDD、已批准 spec 开发时使用。
- 默认 `standard`：读取 spec、制定计划、实现、测试、更新状态。
- `lite`：用于小改动，只要求最小 spec/checklist，不强制生成完整批量计划。
- `strict`：用于多模块或交付型功能，必须检查 arch、测试、验收、状态同步。
- 普通“写代码/修 bug/继续开发/代码调整”不应被本 skill 劫持。

## spec / arch 读取边界

| 信息类型 | 权威来源 | coder 行为 |
|----------|----------|------------|
| 功能目标、用户流程、输入输出 | spec | 必须遵循，不得擅自改写 |
| 验收标准、MT 人工测试用例 | spec | 用于生成自动化测试和人工验收清单 |
| 技术选型、模块边界、API、数据模型 | arch | 存在 arch 时必须遵循；不存在时只能做最小实现假设 |
| 部署方式、启动/关闭命令、软硬件环境 | arch 或项目 `ARCH.md` | 用于实现运行入口和测试前置条件 |
| 轻量实现影响提示 | spec | 只作为提醒，不等同于技术设计 |

> 冲突处理：spec 与 arch 冲突时暂停开发并反馈规范问题。不能默认用 arch 覆盖 spec；如果技术方案要求改变功能行为或验收标准，先修改 spec 并重新审核。

## 核心原则

```
┌─────────────────────────────────────────────────────────────┐
│  1. 规范先行                                                  │
│     每次 coding 前必须检查功能规范；涉及技术决策时必须检查 arch     │
├─────────────────────────────────────────────────────────────┤
│  2. 测试同步                                                  │
│     编写代码时同步更新测试用例，防止偏离用户期望                  │
├─────────────────────────────────────────────────────────────┤
│  3. 可验证优先                                                │
│     优先提供自动化测试或可复现验证；工具型功能优先支持 CLI         │
├─────────────────────────────────────────────────────────────┤
│  4. 自动化为主                                                │
│     自动化测试时跳过人工验证部分，过度依赖人工测试需反馈规范       │
├─────────────────────────────────────────────────────────────┤
│  5. 最小交互                                                  │
│     全程尽量只与用户交流 1-3 次，除非有矛盾或不清楚的问题         │
├─────────────────────────────────────────────────────────────┤
│  6. 计划前置                                                  │
│     展示开发计划，用户同意后再动手                              │
└─────────────────────────────────────────────────────────────┘
```

## 两种处理模式

```
┌─────────────────────────────────────────────────────┐
│                    批量模式                          │
│  用户要求开发多个功能 → AI 自动检索 → 制定计划 → 批量开发  │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│                    单个模式                          │
│  用户指定一个功能 → 读取规范 → 编写测试 → 实现 → 更新状态  │
└─────────────────────────────────────────────────────┘
```

## 阶段 0：规范检查（所有模式都必须执行）

```
┌─────────────────────────────────────────────────────────────┐
│ ⚠️  规范检查 - 未通过不允许开始开发                            │
└─────────────────────────────────────────────────────────────┘

检查项：
1. 功能规范文件是否存在？
2. 技术规范文件是否存在？（简单功能可省略；多模块/软硬件/部署/API/数据模型相关不可省略）
3. 验收标准是否清晰可测试？
4. 若存在 arch，技术选型、运行环境、验证入口是否明确定义？
5. spec 与 arch 是否存在冲突？

如果发现问题 → 列出问题清单，询问用户是否补充规范
```

## 阶段 1：理解与澄清

### Step 1.1: 读取并理解规范

```
1. 读取功能规范 .spec.md
2. 读取项目级 ARCH.md 和功能级 .arch.md（如果有）
3. 梳理验收标准清单
4. 从 spec 识别功能目标、用户流程、输入输出、验收标准
5. 从 arch 识别技术选型、模块/API、数据模型、部署和验证条件
```

### Step 1.2: 检查规范完整性

```
逐项检查验收标准：

□ [001] 验收标准是否可测试？
        → 如果不可测试，标记并询问用户

□ [002] 是否有明确的输入输出？
        → 如果模糊，标记并询问用户

□ [003] 是否有边界条件和异常处理？
        → 如果缺失，标记并询问用户

□ [004] arch 中的技术方案是否可实现？
        → 如果有问题，标记并询问用户

□ [005] spec 与 arch 是否冲突？
        → 如果冲突，暂停开发，要求先修正规范
```

### Step 1.3: 检测问题

```
检查用户需求是否存在：
1. 前后矛盾
2. 逻辑不通
3. 模糊不清
4. 遗漏边界情况

如果发现问题 → 主动提问，不带预设继续
```

### Step 1.4: 收集疑问

```
如果有任何不清楚的地方，在开始开发前必须确认：

❓ 提问清单：
1. {问题1}
2. {问题2}
3. {问题3}

请用户回答后，继续下一步骤。
```

> **重要**：这个阶段可能需要多次交流直到没有疑问。但这是必要的，因为coding开始后再发现规范问题代价更大。

## 阶段 2：制定开发计划

### Step 2.1: 分析功能拆分

```
将功能拆分为最小可开发单元：

| 子任务 | 依赖项 | 预计工作量 | 测试方式 |
|-------|-------|-----------|---------|
| T1: 数据模型 | 无 | 小 | 自动化 |
| T2: API接口 | T1 | 小 | 自动化 |
| T3: 业务逻辑 | T2 | 中 | 自动化 |
| T4: CLI工具 | T3 | 小 | 自动化 |
| T5: 界面交互 | T4 | 中 | 人工 |
```

### Step 2.2: 识别可验证与 CLI 需求

```
┌─────────────────────────────────────────────────────────────┐
│  🔧 可验证性与 CLI 检查                                        │
├─────────────────────────────────────────────────────────────┤
│  以下功能建议优先提供 CLI 或脚本入口，再做界面：                  │
│  • 数据查询/搜索                                              │
│  • 数据增删改                                                │
│  • 文件导入导出                                              │
│  • 定时任务管理                                              │
│  • 状态切换/批量操作                                         │
└─────────────────────────────────────────────────────────────┘

识别结果：
□ 用户操作入口 → 界面 + 可复现验证入口
□ 后台处理逻辑 → 自动化测试或脚本入口
□ 数据管理功能 → CLI/脚本优先（界面可选）
```

### Step 2.3: 生成开发计划

```
📋 开发计划

【功能】{功能名称}
【规范】{规范编号}
【目标】{一句话目标}

─────────────────────────────────────────

开发顺序：

  Step 1: 数据模型
  ├── 任务：设计并实现数据模型
  ├── 依赖：无
  └── 交付：数据模型代码 + 单元测试

  Step 2: 可验证核心入口
  ├── 任务：实现 CLI/脚本/API 测试入口
  ├── 依赖：Step 1
  ├── 交付：可复现入口 + 自动化测试
  └── 注意：工具型操作优先支持命令行，业务界面按项目实际设计

  Step 3: 业务逻辑
  ├── 任务：实现核心业务逻辑
  ├── 依赖：Step 2
  └── 交付：业务逻辑代码 + 自动化测试

  Step 4: 界面交互（如果需要）
  ├── 任务：实现用户界面
  ├── 依赖：Step 3
  └── 交付：界面代码 + 人工测试清单

─────────────────────────────────────────

测试策略：
□ 自动化测试：{X} 项（数据模型、API、CLI、业务逻辑）
□ 人工测试：{Y} 项（仅限界面交互和用户体验）

预计自测完成次数：{N} 次运行自动化测试
```

### Step 2.4: 展示计划并征询同意

```
═══════════════════════════════════════════════════════════════
📋 开发计划已生成，请在确认后开始执行

【功能】{功能名称}
【规范】{规范编号}

开发步骤：
  1. 数据模型设计
  2. CLI 命令实现
  3. 业务逻辑编码
  4. 界面交互（可选）

测试方式：
  • 自动化测试：{X} 项（全程自动验证）
  • 人工测试：{Y} 项（仅界面相关）

─────────────────────────────────────────

💡 提示：
• 开发过程中无需用户干预
• 自测全部通过后主动通知验收
• 如遇问题会主动提问

请选择：
1. ✅ 确认，开始开发
2. ✏️ 调整计划（跳过某步骤/调整顺序）
3. ❌ 取消，稍后再说
═══════════════════════════════════════════════════════════════
```

> **重要**：获得用户明确同意后才开始 coding。如果用户选择调整，先修改计划再重新确认。

## 阶段 3：TDD 开发执行

### Step 3.0: 更新状态为"开发中"（必须执行）

```
┌─────────────────────────────────────────────────────────────┐
│  📋 状态更新                                                │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 更新 {ID}-{NAME}.spec.md 中的状态字段：                   │
│     状态：已批准 → 开发中                                     │
│                                                              │
│  2. 更新 SPEC.md 功能列表中的状态列：                         │
│     | {ID} | {NAME} | ... | 开发中 | ... |                   │
│                                                              │
│  3. 更新 STATUS.md，必要时追加 TRACK.md：                                          │
│     - {DATE} 开发中 开始开发                                  │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

> **重要**：必须在开始编码前完成状态更新，确保状态始终与实际进展同步。

### Step 3.1: 先写测试（测试驱动）

```
每个子任务都遵循：

  1. 写一个会失败的测试
  2. 运行测试确认失败
  3. 写最简代码让测试通过
  4. 重构代码
  5. 运行所有测试确认通过

测试文件位置：az-sdd/test/cases/{ID}-{TASK}-{N}.test.ts
```

### Step 3.2: 可验证优先实现

```
对于需要用户操作的功能：

  1. 先实现可测试的核心逻辑
  2. 为工具型功能提供 CLI/脚本入口
  3. 编写自动化测试或可复现验证步骤
  4. 界面作为调用核心逻辑的一层，而不是唯一验证方式

CLI 测试覆盖：
  • 帮助信息
  • 参数解析
  • 输入验证
  • 输出格式
  • 错误处理
  • 边界情况
```

### Step 3.3: 自动化测试跳过人工部分

```
测试分类：

【自动化测试 - 全部执行】
  □ 数据模型测试
  □ API 接口测试
  □ CLI 命令测试
  □ 业务逻辑测试
  □ 边界条件测试
  □ 异常处理测试

【人工测试 - 暂时跳过】
  □ 界面布局是否美观
  □ 颜色是否符合预期
  □ 动画效果是否流畅
  □ 用户体验是否顺畅

⚠️  如果自动化测试覆盖率低于 70%，需要反馈给技术规范：
    "此功能过度依赖人工测试，建议拆分或重新设计以提高可测试性"
```

### Step 3.4: 持续自测

```
每完成一个子任务：
1. 运行该任务的测试
2. 运行所有相关测试（回归测试）
3. 生成测试报告
4. 如果失败：修复代码，不询问用户
```

## 阶段 5：记录开发证据并更新状态

### Step 5.1: 记录开发证据

coding 阶段不生成 HTML 报告。只把本次开发证据写入编码任务文档和相关 Markdown/索引文件，供 `/az-sdd-track` 统一汇总生成项目报告。

必须记录：

- 实现摘要：本次完成的功能点和主要修改范围
- 自动化测试：测试命令、通过数量、失败项（如有）
- 人工验收项：需要 `/az-sdd-tester` 验证的 MT 测试项
- 遗留问题：阻塞、风险、后续任务

### Step 5.2: 更新状态

```
┌─────────────────────────────────────────────────────────────┐
│  📋 状态更新                                                │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 更新编码任务文档：                                       │
│     az-sdd/coding/{TIMESTAMP}-plan.coding.md                │
│     - 记录实现摘要、测试结果、人工验收项、遗留问题             │
│                                                              │
│  2. 更新 {ID}-{NAME}.spec.md（必须执行）：                    │
│     - 状态字段：测试中 → 待验收                               │
│     - 在验收标准部分标注自动化测试已通过                       │
│     - ⚠️ 在规范文件末尾添加 ## 测试用例 章节                   │
│       必须包含 MT001, MT002... 格式的测试用例                  │
│       test 阶段会从规范文件读取此章节！                        │
│                                                              │
│  3. 更新 SPEC.md 功能列表：                                   │
│     | {ID} | {NAME} | ... | 待验收 | ... |                 │
│                                                              │
│  4. 更新 STATUS.md，必要时追加 TRACK.md：                                          │
│     - {DATE} 待验收 自动化测试完成，等待人工验收               │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

**⚠️ MT 测试用例格式要求**：

```markdown
## 测试用例

### MT001 {测试项名称}
- **测试步骤**：1. ... 2. ... 3. ...
- **预期结果**：...
- **验收标准**：[对应验收标准编号]
```

**⚠️ 禁止行为**：
- ❌ 只更新状态，不生成测试用例
- ❌ 验收标准与测试用例不对应
- ❌ 测试用例缺少测试步骤或预期结果

```typescript
      expect(stdout).toContain('Usage:');
    });

    it('should handle valid input', async () => {
      const result = await executeCLI(['{command}', 'create', '--name', 'test']);
      expect(result.exitCode).toBe(0);
    });

    it('should handle invalid input', async () => {
      const result = await executeCLI(['{command}', 'create', '--name', '']);

      expect(result.stderr).toContain('error');
    });

    it('should output correct format', async () => {

    });
  });
});
```

## 错误处理

| 情况 | 处理方式 |
|------|---------|
| 规范文件不存在 | 暂停开发，询问用户 |
| 规范不完整 | 列出缺失项，询问用户补充 |
| 自动化测试失败 | 修复代码，不打扰用户 |
| 发现用户需求矛盾 | 暂停开发，主动提问确认 |
| CLI 难以实现某个功能 | 反馈给技术规范，寻求替代方案 |
| 人工测试占比过高 | 反馈给规范，要求改进设计 |
| 批量模式有规范问题 | 暂停，询问跳过还是补充 |
