## 一、AI Coding 的三阶段

首先，我们来梳理一下 AI Coding 发展的三个阶段。这三个阶段不是突然出现的，它们是技术进步和需求演变的结果。

> **说明**：以下阶段划分是基于个人实践经验的总结，并非业界统一标准。不同开发者可能会有不同的划分方式。

### 1.1 第一阶段：Tab Coding（2023年雏形 / 2025年4月命名）

**故事背景**：

2023 年，Cursor 编辑器推出了 **Tab** 功能，初期为 AI 代码补全工具。2025 年 4 月 4 日，Neon 博客首次提出 **Tab Coding** 概念，定义为"通过 Tab 键一键接受 AI 预测代码"的编程范式。

那时候我第一次用 Cursor 的 Tab 功能，印象非常深刻——我正在写一个 HTTP 请求的封装函数，写到第三行的时候，AI 直接给我补全了整个函数，包括异常处理，我只需要按一下 Tab 键确认。

当时的感受是：**AI 好像真的懂我在写什么**。

**代表工具**：

- Cursor（2023年推出 Tab 功能）
- GitHub Copilot
- Tabnine

**核心交互方式**：

IDE 插件，AI 预测代码，**Tab 键一键确认**。你写一个函数名，写几行注释，AI 自动预测剩余代码，你按 Tab 接受。

**核心特点**：**人机协作、AI 预测、Tab 确认**，强调"边写边补、无缝衔接"。

**它解决了什么问题**：

第一个阶段解决的是**效率问题**——重复代码不用再手动敲了。比如：

```python
# 我只需要写这几行：
def get_user
# AI 自动预测，我按 Tab 确认：
def get_user(user_id: int) -> dict:
    """Get user by ID."""
    return db.query(f"SELECT * FROM users WHERE id = {user_id}")
```

这样的模式匹配代码，AI 预测的速度比手工输入快得多。

**局限性**：

但问题很快就暴露出来了：

1. **只能生成单点代码片段**——AI 不知道你这个函数在整个项目中扮演什么角色
2. **无全局理解能力**——上下文只有当前编辑的文件
3. **复杂逻辑它帮不上忙**——你需要先把逻辑设计好，它才能帮你填充代码

我用一句话总结第一阶段：**AI 是个好助手，但只是个助手**。

---

### 1.2 第二阶段：Vibe Coding（2025年2月2日提出）

**故事背景**：

2025 年 2 月 2 日，Andrej Karpathy（OpenAI 联合创始人）在 X（原 Twitter）发文，首次提出 **Vibe Coding** 概念，定义为"用自然语言描述需求，AI 生成代码，人只把控方向"。2025 年 3 月，被韦氏词典列为"流行俚语"；11 月当选**柯林斯词典年度词汇**。

我开始用 ChatGPT/Claude 帮我写代码。有一个项目需要实现一个异步任务队列，我跟 AI 描述了一下需求，它给了我一个完整的实现方案。

那一刻我意识到：**原来编程可以用自然语言**。

**代表工具**：

- ChatGPT
- Claude
- Copilot Chat
- Cursor Composer

**核心交互方式**：

对话窗口，**纯自然语言描述需求**。你可以"告诉"AI 你要做什么，而不是手动写代码。

**核心特点**：**纯自然语言驱动、信任 AI、结果导向**，强调"能跑就行、跟着感觉走"。

**它解决了什么问题**：

Vibe Coding 解决的是**设计问题**——你不需要从第一行代码开始写起了。

举个例子，你想实现一个"TBox远程车窗控制"功能，你可以这样描述：

```
帮我实现远程车窗控制功能：
1. 支持四门独立升降控制
2. 支持防夹手功能（检测到障碍物时自动上升）
3. 支持限位停止（车窗升到顶自动停止）
4. 状态变化时实时上报云端
```

AI会给你一个完整的方案，包括CAN信号定义（信号名、ID、周期、字节定义）、状态机设计、故障处理策略。

**比 Tab Coding 强在哪里**：

| 维度 | Tab Coding | Vibe Coding |
|------|---------|---------|
| 生成粒度 | 单函数 | 功能模块 |
| 理解能力 | 代码前缀 | 自然语言描述 |
| 迭代方式 | 重写 | 对话修改 |

**局限性**：

但问题也随之而来，而且是更严重的问题：

1. **上下文窗口有限**——AI 只记得最近 N 条对话，你没法问它"这个项目里用户模块的整体设计是什么"
2. **多文件协作能力弱**——它能生成单个文件，但不理解多个文件之间的依赖关系
3. **缺乏项目规范约束**——每次对话都是独立的，生成的代码风格可能不一致
4. **自然语言有歧义性**——你说"发送车门状态"，AI可能理解成查询车门状态并上传云端，也可能理解成直接操控车门动作

我用一句话总结第二阶段：**AI 是个聪明的助手，但它不懂你的项目**。

---

### 1.3 第三阶段：Spec Coding（2025年中提出，思想起源2004年）

**故事背景**：

**思想起源**：2004 年，微软研究院提出 **Spec#**，将规范（Spec）与代码绑定，奠定"先规范后代码"思想。

**范式命名**：2025 年中，在 Vibe Coding 热潮后，社区提出 **Spec Coding**，作为对"无规范依赖 AI"的反思，强调**先写规范（Spec.md）、再让 AI 严格实现**。

我参与了一个TBox项目的开发。这个项目有5个开发人员同时工作，我们开始用AI生成代码。但很快问题出现了：

- 开发者A定义的CAN信号ID是0x201，开发者B定义的是0x301，ID冲突
- 每个人对"远程控制"的理解都不一样，有人理解为MQTT云端控制，有人理解为蓝牙近场控制
- 三个月后，代码库里同一个功能有三种不同的实现方式

我们意识到：**需要一个统一的东西来约束AI**。

这就是 **Spec Coding（规范驱动编程）** 诞生的背景。

**核心理念**：

Spec Coding 不再是"告诉 AI 要做什么"，而是"**先让 AI 理解我们要做什么、有什么约束、交付标准是什么**"。

流程变成这样：

```
需求描述 → 规范文档(Spec) → 技术约束 → 代码实现 → 测试验收
```

**核心特点**：**规范先行、文档即代码、严格验收**，强调"精确可控、可测试、可维护"。

**它解决了什么问题**：

1. **一致性问题**——所有人基于同一份规范工作，AI 生成的代码风格统一
2. **可维护性问题**——规范文档记录了技术选型和设计决策，新人能快速上手
3. **质量保证问题**——规范文档内置测试用例，AI 生成的代码可验收
4. **多人协作问题**——规范文档是唯一的真实来源，解决认知不一致

**核心升级**：

Spec Coding 和前两个阶段最大的区别是：**AI 不仅生成代码，还能理解项目规范、遵循技术约束、维护状态**。

## 二、各阶段的问题与解决

这部分我用一张表格来对比三个阶段的能力边界，帮助大家建立更清晰的认识。

### 2.1 对比表格

| 维度 | Tab Coding | Vibe Coding | Spec Coding |
|------|---------|---------|---------|
| **提出时间** | 2023年雏形<br>2025年4月命名 | 2025年2月2日 | 2025年中命名<br>思想起源2004年 |
| **核心提出者** | Cursor / Neon 博客 | Andrej Karpathy | 社区对 Vibe Coding 的反思 |
| **输入形式** | 代码前缀 | 自然语言需求 | 结构化规范文档 |
| **生成粒度** | 单函数/单文件 | 功能模块 | 完整功能（含边界、测试） |
| **上下文范围** | 当前编辑文件 | 最近 N 条消息 | 完整项目规范+状态 |
| **一致性保证** | 无保证 | 依赖 prompt 质量 | 规范强制约束 |
| **测试** | 无 | 手动补充 | 规范内置测试用例 |
| **协作** | 无 | 无 | 多人共享规范 |
| **状态追踪** | 无 | 无 | 完整生命周期状态机 |

### 2.2 痛点分析

**Tab Coding 痛点**：

我用一个场景来说明。假设你要开发TBox的远程车窗控制功能，在 Tab Coding 阶段：

- AI只能帮你写单个函数，比如"解析车窗状态信号"
- 你需要自己设计整个车窗控制的架构
- AI不理解"车窗信号"和"CAN总线"之间的关系
- 你问AI"这个项目CAN信号的字节序是什么"，它不知道

**Vibe Coding 痛点**：

还是TBox车窗控制的场景，在 Vibe Coding 阶段：

- 你可以让AI设计一个"车窗模块"
- 但如果让5个开发者分别描述"车窗控制"，会得到5套不同的设计方案
- 一个月后，有人用信号WINDOW_STATUS_0x201，有人用WINDOW_STS_0x301，ID都不一样
- CAN报文定义也不一致，有人用Intel格式，有人用Motorola格式
- 更可怕的是，没有测试用例，你不知道AI生成的代码在实际车载环境里能不能工作

**Spec Coding 的解决思路**：

Spec Coding 通过**规范文档**来约束：

- 在写代码之前，先把"车窗控制"的设计决策写成规范文档
- 规范文档明确规定：CAN信号ID=0x201、周期100ms、Intel字节序、故障时默认车窗保持当前位置
- 规范文档还内置了测试用例（包括HIL硬件在环测试），代码完成后必须通过测试
- 规范文档记录状态：当前在什么阶段、是否符合GB/T标准

这样，不管是谁来开发这个功能，只要遵守规范，出来的代码就是一致的。

## 三、为什么需要 Spec？

这部分我重点讲一下 Spec 规范到底是什么，以及为什么我们需要它。

首先介绍一下，**Spec 是 Specification（规范）的缩写**。在软件开发领域，Spec 指的是对功能、接口、行为的精确描述文档。在 AI 编码的语境下，Spec 是连接人类意图和 AI 实现的桥梁。

### 3.1 自然语言的歧义性问题

我先问大家一个问题：**"远程开锁"这四个字，在TBox开发中，可能有几种理解？**

我数了一下，至少有六种：

1. 车主手机APP远程解锁车门
2. 4S店技师近场诊断时解锁OBD接口
3. 车队管理员解锁运营车辆（营运场景）
4. 二手车交易时的解锁权限变更
5. 交警/保险公司应急解锁
6. 车辆休眠后的唤醒解锁

如果你让 Vibe Coding 阶段的AI实现"远程开锁"功能，它可能只理解其中一种。但你的产品需求可能是多场景并存、需要权限分级。

这就是自然语言的歧义性——**同一个功能描述，在汽车行业可能有完全不同的业务上下文**。

Spec通过精确定义**功能边界**来消除歧义：

```markdown
## 功能边界

### 做什么
- 支持车主APP远程解锁车门（限定距离：无限制）
- 支持蓝牙近场解锁（距离车辆5米内）
- 解锁成功后车辆进入ready状态（可启动）

### 不做什么
- 不支持4S店远程解锁（需走诊断CAN总线）
- 不支持应急解锁（将由紧急救援模块处理）
- 不支持营运车队远程强制解锁（将走专用调度系统）
- 不支持在车辆碰撞报警状态下解锁（安全优先）

### 权限约束
- 仅车主持有解锁权限
- 解锁记录需同步至云端
- 单日解锁次数上限：10次
```

### 3.2 多人协作的认知对齐

第二个问题：**多人协作时，如何保证大家的理解是一致的？**

我见过最糟糕的情况是，产品提了一个需求，5个开发人员各自开发，最后集成的时候发现：

- 开发者A的"远程空调"包含了座椅加热
- 开发者B的"远程空调"只有制冷和制热
- 开发者C的"远程空调"还有除雾功能
- CAN报文里三个不同的信号定义，ID各不相同

大家都在开发"远程空调控制"功能，但每个人理解的"空调"是不一样的。

Spec作为**唯一的真实来源**，所有人基于同一份文档工作：

```markdown
## CAN信号定义（空调控制）

### 空调控制信号：AC_CTRL_0x123
| 信号名 | 字节位置 | 位定义 | 值范围 | 说明 |
|--------|---------|-------|-------|------|
| ac_power | 0[0] | 1bit | 0/1 | 空调电源状态 |
| ac_mode | 0[1-3] | 3bit | 0-4 | 0:关闭 1:制冷 2:制热 3:自动 4:除雾 |
| ac_temp | 1[0-7] | 8bit | 16-30 | 目标温度(℃) |
| fan_speed | 2[0-5] | 6bit | 0-7 | 风扇转速等级 |
```

### 3.3 测试用例缺失

第三个问题：**没有测试用例的代码，质量怎么保证？**

AI生成的代码，在 Vibe Coding 阶段，你只能手动写测试用例。但汽车行业的测试不是那么简单：

- 你不能"随便测测"，TBox是要上车的，出了bug可能涉及人身安全
- 你不能只测功能，还要测CAN通信、诊断协议、故障注入
- 你不能只测"正常情况"，还要测"极端环境"（低温启动、高温休眠）

Spec内置测试用例，AI生成代码后自动运行验收：

```markdown
## 测试用例

| 用例编号 | 用例名称 | 测试类型 | 验证结果 |
|---------|---------|---------|---------|
| MT001 | 远程解锁命令下发成功 | HIL自动化 | 待验证 |
| MT002 | 信号超时（500ms无响应）处理 | HIL自动化 | 待验证 |
| MT003 | 车内CAN总线故障时安全策略 | 人工测试 | 待验证 |
| MT004 | 低温-40℃环境解锁功能 | 环境测试 | 待验证 |
| MT005 | 高频解锁请求（10次/分钟）限频 | 自动化 | 待验证 |
```

### 3.4 大型项目的维护性

第四个问题：**项目规模扩大后，AI生成的代码还能维护吗？**

我在 Vibe Coding 阶段用过AI开发一个TBox的远程控制模块，包含门锁、车窗、空调等8个功能。半年后：

- 第一个功能是谁开发的、原始需求是什么，没人记得了
- AI当时为什么这样定义CAN信号ID，不清楚
- 新的需求来了（比如增加座椅加热控制），我不知道怎么和现有CAN信号兼容
- 有一个bug（比如解锁后车窗会自动下降），我不敢改，怕影响其他功能
- 客户要做GB/T32960认证，我不知道哪些代码需要重新审查

Spec文档记录了所有的设计决策和技术约束：CAN信号定义、故障诊断协议、安全策略、行业标准合规性。新人可以通过阅读Spec快速理解TBox的功能架构，而不是去读那几千行没有注释的C代码。

## 四、Spec 规范的核心组成

接下来我们详细看一下，一份完整的 Spec 规范应该包含哪些部分。

### 4.1 功能边界

功能边界回答一个问题：**这个功能做什么、不做什么？**

```markdown
## 功能边界

### 核心功能
1. 车主APP远程解锁车门
2. 蓝牙近场解锁（距离车辆5米内）
3. 解锁成功后整车进入ready状态

### 边界情况处理
- 车辆处于碰撞报警状态时，拒绝解锁，提示"安全模式下不可操作"
- 网络信号弱时，解锁请求超时时间延长至3秒
- 单日解锁次数超过10次时，触发风控审核
- 车辆休眠时，解锁请求需要先唤醒TBox（约2秒）

### 不包含的功能
- 4S店诊断模式解锁（将单独开发诊断模块）
- 营运车队强制调度解锁（将走调度系统接口）
- 远程鸣笛/闪灯（将在其他功能模块实现）
```

### 4.2 技术约束

技术约束是Spec中最重要的部分。技术约束回答：**这个功能用什么协议、有什么通信要求、安全策略？**

```markdown
## 技术约束

### 通信协议
- TBox与云平台：MQTT over TLS 1.2
- TBox与车载CAN：HS-CAN 500kbps（符合ISO 11898）
- 近场解锁：BLE 4.2

### CAN信号定义
- 车门状态信号：DOOR_STATUS_0x101（周期100ms）
- 解锁命令信号：DOOR_UNLOCK_0x102（事件触发）
- TBox心跳信号：TBOX_HEARTBEAT_0x100（周期1s）

### 诊断协议
- 符合UDS（ISO 14229）诊断协议
- 故障码符合DTC标准（ISO 15031）

### 安全约束
- 命令使用AES-256加密
- OTA升级需双重签名验证
- 近场解锁需手机SIM卡鉴权
- 解锁记录完整上云，不可篡改

### 实时性要求
- 云端命令下发到CAN信号输出：<500ms
- 近场解锁响应时间：<200ms
- TBox休眠唤醒时间：<2s
```

## 五、从 Spec 到代码的流程

最后一部分，我们来看一下完整的 Spec 驱动开发流程，以及为什么这个流程能解决我们之前提到的那些问题。

### 5.1 标准流程

```
需求描述 → Spec 规范 → 技术审核 → 代码实现 → 测试验收 → 状态更新
    ↓         ↓       ↓          ↓           ↓
  用户      AI+用户   产品+技术    AI+规范     规范+测试
```

### 5.2 流程详解

**第一步：需求描述**

用户（产品/业务方）描述需求，这时候用的是自然语言。比如："车主希望夏天开车前能远程开启空调。"

**第二步：Spec 规范**

AI从需求中提取功能边界和技术约束，生成规范文档（包括CAN信号定义、通信协议、安全策略）。用户审核确认。

**第三步：技术审核**

对于TBox功能，技术方案需要技术负责人审核确认（特别是CAN信号定义和故障诊断协议）。

**第四步：代码实现**

AI按照规范文档生成代码。规范文档就是代码的蓝图，AI不会擅自决定CAN信号的ID或周期。

**第五步：测试验收**

运行规范文档中内置的测试用例（包括HIL硬件在环测试），验证代码是否符合规范。

**第六步：状态更新**

更新规范文档中的状态字段，记录开发进度。

### 5.3 为什么这个流程能解决问题？

| 我们之前提到的问题 | 解决方案 |
|------------------|---------|
| 自然语言歧义性 | Spec 精确定义功能边界，消除歧义 |
| 多人认知不一致 | 统一规范文档，所有人基于同一份文档工作 |
| 测试用例缺失 | Spec 内置验收测试用例 |
| 技术债务累积 | Spec 记录技术约束，新功能必须遵循 |
| 流程不透明 | 状态机追踪，每个阶段清晰可见 |
| 代码不一致 | AI 严格按规范生成，强制一致性 |

## 六、总结与练习

### 6.1 关键知识点回顾

今天我们讲了三个部分的内容：

**第一部分：AI Coding 三阶段**

| 范式 | 提出时间 | 核心提出者 | 核心特点 | 局限 |
|------|---------|-----------|---------|------|
| Tab Coding | 2023年雏形<br>2025年4月命名 | Cursor / Neon 博客 | 人机协作、AI 预测、Tab 确认 | 单点代码 |
| Vibe Coding | 2025年2月2日 | Andrej Karpathy | 纯自然语言驱动、信任 AI、结果导向 | 无项目理解 |
| Spec Coding | 2025年中命名<br>思想起源2004年 | 社区对 Vibe Coding 的反思 | 规范先行、文档即代码、严格验收 | 需要前期投入 |

> 注：时间划分基于标志性工具的发布时间（Copilot 2021年6月、ChatGPT 2022年11月、Cursor 2023年）

**第二部分：为什么需要 Spec**

1. 消除自然语言的歧义性
2. 统一多人协作的认知
3. 内置测试用例保证质量
4. 记录设计决策便于维护

**第三部分：Spec 核心组成**

1. 功能边界（做什么、不做什么）
2. 技术约束（技术栈、API 规范、安全要求）
3. 验收标准（测试用例、性能要求）
4. 状态追踪（当前阶段、阻塞问题）
