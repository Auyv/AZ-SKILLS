## 一、AZ-SDD 整体架构

### 1.1 核心理念

先问一个问题：**理论篇我们学了为什么要用 Spec，那在实际开发中，Spec 文档谁来写、写完之后谁来用、用完之后谁来检查？**

这些听起来像是流程管理的问题。但 AI 时代的流程管理不一样了——我们需要的是一个**让 AI 和人类都能理解的规范系统**。

这就是 AZ-SDD 设计的核心理念：

> **让用户只需描述业务，AI 自动完成从需求规范到代码测试的全流程。**

关键词是**自动**。不是"AI 辅助你"，而是"AI 自动完成"。

### 1.2 9 个 SKILL 总览

AZ-SDD 提供了 9 个技能模块，每个模块对应开发流程中的一个环节：

| SKILL | 命令 | 阶段 | 核心作用 |
|-------|------|------|---------|
| az-sdd-init | `/az-sdd-init` | 项目初始化 | 创建项目档案目录结构 |
| az-sdd-spec | `/az-sdd-spec` | 功能规范 | 编写功能规范，AI 提取技术约束 |
| az-sdd-arch | `/az-sdd-arch` | 技术规范 | 复杂技术决策独立文档化（可选） |
| az-sdd-coding | `/az-sdd-coding` | 代码实现 | 按照规范实现功能代码 |
| az-sdd-test | `/az-sdd-test` | 测试验收 | 交互式人工测试验收 |
| az-sdd-track | `/az-sdd-track` | 状态追踪 | 管理项目工作状态 |
| az-sdd-feedback | `/az-sdd-feedback` | 用户反馈 | 智能反馈处理 |
| az-sdd-rules | `/az-sdd-rules` | 规则清单 | 显式检查流程、状态和同步规则 |

这里我特别提一下 **az-sdd-rules**。v3 不假设平台能自动拦截其他 SKILL；日常使用优先从 `/az-sdd-next` 进入，或由当前 skill 显式执行规则检查。

### 1.3 流程图

完整的开发流程是这样的：

```
init → spec → arch(可选) → coding → test → track → feedback
  │      │                    │        │       │         │
  └──────┴────────────────────┴────────┴───────┴─────────┘
                         规则守卫自动监控
```

我们一个个来看：

**init**（初始化）：建立项目档案目录结构。这一步做完后，项目里会有一个 `az-sdd/` 目录，用来存放所有的规范文档。

**spec**（功能规范）：编写功能规范文档。AI 会从你的需求描述中自动提取技术约束，生成一份结构化的规范文档。

**arch**（技术规范，可选）：如果功能涉及复杂的技术决策（比如架构变更、引入新技术），需要单独的技术规范文档。简单功能可以跳过这一步。

**coding**（代码实现）：按照规范文档生成代码。AI 在这个阶段会严格遵循 spec 中的技术约束。

**test**（测试验收）：运行规范文档中内置的测试用例，进行验收。

**track**（状态追踪）：更新项目状态，记录变更历史。

**feedback**（用户反馈）：处理用户反馈，可能是 Bug 修复，可能是新功能需求。

### 1.4 快速流程和迭代流程

除了主流程，AZ-SDD 还支持两种特殊流程：

**快速流程**（适用于小型功能或紧急修复）：

```
spec → coding → test
```

比如修复一个 Bug，可能只需要改一行代码，走快速流程就够了。

**迭代流程**（适用于基于反馈的优化）：

```
feedback → spec → coding → test → track
```

用户反馈说"远程开锁有时候太慢了，要3秒以上"，走迭代流程优化性能。

## 二、主流程详解

### 2.1 init → spec

**init 阶段**：项目初始化。

你执行 `/az-sdd-init`，系统会在当前目录下创建 `az-sdd/` 目录结构：

```
workspace/
├── az-sdd/                    # 规范档案目录
│   ├── init.md               # 项目初始化信息
│   ├── track.md              # 工作状态追踪记录
│   ├── SPEC.md               # 功能规范索引
│   ├── ARCH.md               # 技术规范索引
│   ├── FEEDBACK.md           # 用户反馈索引
│   ├── spec/                 # 功能规范文档
│   ├── arch/                 # 技术规范文档
│   ├── test/                 # 测试文件
│   └── feedback/             # 用户反馈文档
└── code/                      # 代码实现目录
```

**这里有一个强制规定**：代码文件必须统一放在 `code/` 目录下，禁止将代码文件放入 `az-sdd/` 目录。这个规定的目的是保持 `az-sdd/` 目录只包含规范文档，便于管理和审计。

**spec 阶段**：功能规范编写。

这是最核心的阶段之一。当你描述一个功能需求时，AI 会：

1. **理解需求**：和你对话，理解你要做什么
2. **提取技术约束**：自动从需求中识别技术要求（用什么数据库、用什么框架、安全要求等）
3. **生成规范文档**：按照标准模板生成结构化的规范文档
4. **内置测试用例**：在规范文档中内置验收测试用例

生成的规范文档大概长这样：

```markdown
# 功能规范：远程车门控制

## 基本信息
- 功能编号：0010
- 功能名称：远程车门控制
- 所属模块：远程控制
- 状态：已批准

## 功能边界
### 做什么
- 支持车主APP远程解锁/锁止车门
- 支持蓝牙近场解锁（距离车辆5米内）
- 解锁成功后整车进入ready状态

### 不做什么
- 不支持4S店诊断模式解锁
- 不支持营运车队强制调度解锁
- 不支持碰撞报警状态下的解锁

## 技术约束
- 通信协议：MQTT over TLS 1.2
- CAN信号：DOOR_UNLOCK_0x102（事件触发）
- 安全：AES-256加密命令，近场解锁需SIM卡鉴权
- 实时性：云端到CAN输出<500ms

## 测试用例
| 用例编号 | 用例名称 | 测试类型 |
|---------|---------|---------|
| MT001 | 远程解锁命令下发成功 | HIL自动化 |
| MT002 | 信号超时处理 | HIL自动化 |
| MT003 | CAN总线故障时安全策略 | 人工测试 |
| MT004 | -40℃环境解锁 | 环境测试 |

## 状态
- 当前状态：已批准
- 创建时间：2024-06-01
```

### 2.2 arch（可选）

**arch 阶段**：技术规范。

不是所有功能都需要这一步。只有当功能涉及**复杂技术决策**时才需要，比如：

- 引入新的技术栈（原来用 MySQL，现在要引入 MongoDB）
- 架构变更（从单体架构改为微服务）
- 重构（大规模代码重构）
- 新技术调研（评估是否要用 WebAssembly）

简单功能可以直接跳过 arch 阶段。

### 2.3 coding → test

**coding 阶段**：代码实现。

这是最关键的阶段。AI 在生成代码时会严格遵循 spec 中的规范：

- 技术栈必须和 spec 一致
- API 风格必须和 spec 一致
- 数据模型必须和 spec 一致
- 测试用例必须通过

AZ-SDD 的 coding 有几个核心原则：

1. **规范先行**：coding 前必须先有已批准的规范
2. **测试同步**：测试用例和代码同步编写（TDD 流程）
3. **CLI-First**：所有功能支持命令行操作
4. **自动化为主**：减少人工交互
5. **计划前置**：每次 coding 前生成执行计划

在批量开发模式下（多个功能同时开发），AI 还会：
- 自动检索未完成的功能规范
- 分析功能间的依赖关系
- 生成功能实现前趋图
- 按顺序执行编码任务

**test 阶段**：测试验收。

在开始测试之前，有一个 Step 0 前置检查需要完成：

- 应用启动脚本已创建并测试通过
- 应用关闭脚本已创建并测试通过

这个前置检查的目的是确保测试环境可以正常启动和关闭。

测试阶段会：
- 读取规范中的测试用例
- 生成交互式 HTML 验收页面
- 人工确认测试结果
- localStorage 保存测试进度
- 验收通过后自动更新状态

### 2.4 track → feedback

**track 阶段**：状态追踪。

每次状态变更，必须同步更新所有相关文档：

| 文件 | 更新内容 |
|------|---------|
| 规范文件本身 | 状态字段 |
| SPEC.md | 功能列表中的状态列 |
| track.md | 变更历史记录 |
| coding.md（批量模式） | 当前编码进度 |

**feedback 阶段**：用户反馈处理。

用户反馈分为三种类型：

1. **Bug**：功能不工作
2. **改进建议**：功能能用，但可以更好
3. **新功能需求**：需要新功能

每种类型有不同的处理流程：

- Bug：定位问题 → 修复代码 → 测试验收
- 改进建议：评估影响 → 确认实现方案 → 迭代开发
- 新功能需求：创建新规范 → 进入主流程

## 三、状态机设计

### 3.1 9 个状态定义

AZ-SDD 定义了 9 个状态，组成完整的功能生命周期：

| 状态 ID | 中文名称 | 图标 | 说明 |
|---------|---------|------|------|
| draft | 草稿 | 📋 | 规范文档已创建，待审核 |
| reviewing | 审核中 | 👁️ | 规范正在审核，等待确认 |
| approved | 已批准 | ✅ | 规范审核通过，可以开始开发 |
| developing | 开发中 | 🔨 | 正在按照规范实现 |
| testing | 测试中 | 🧪 | 自动化测试执行中 |
| acceptance | 待验收 | 🎯 | 等待人工测试验收 |
| completed | 已完成 | ✅ | 人工验收通过 |
| released | 已发布 | 🚀 | 功能已正式发布 |
| blocked | 阻塞 | 🚧 | 遇到阻塞问题，需要解决 |

### 3.2 状态转换规则

标准的状态流转是这样的：

```
草稿 → 审核中 → 已批准 → 开发中 → 测试中 → 待验收 → 已完成 → 已发布
                                                            ↑
                                                        （可回退）
```

几个关键规则：

**正向流转**：每个箭头代表一个 SKILL 操作的完成。比如 spec 审核通过，状态从"审核中"变为"已批准"。

**回退机制**：在某些情况下，状态可以回退。比如测试发现代码不符合规范，状态从"待验收"回退到"开发中"。

**阻塞状态**：`blocked` 状态比较特殊，可以从任何开发状态进入。比如开发中遇到了技术难题，可以标记为阻塞状态，处理完后再继续。

**规则守卫**：az-sdd-rules 会自动监控状态转换是否符合规则。比如你不能在没有规范的情况下开始 coding（状态必须是"已批准"以上）。

### 3.3 状态同步更新机制

这是一个经常被忽视但非常重要的规则：**状态变更必须同步更新所有相关文档**。

为什么会强调这一点？我见过太多项目，规范文件是一个状态，索引目录是另一个状态，代码仓库又是另一个状态。到最后没人知道功能的真实状态是什么。

AZ-SDD 的同步规则要求：

每次状态变更必须同步更新：
- 规范文件本身的状态字段
- SPEC.md 中功能列表的状态列
- track.md 中的变更历史记录

同步检查清单：
- [ ] SPEC.md 中该功能的状态列是否与规范文件一致
- [ ] track.md 中是否已记录本次状态变更（时间、原因、变更前后状态）

## 四、SKILL 详解

### 4.1 az-sdd-spec：功能规范编写

**两种模式**：

1. **单一模式**：为一个功能编写规范
2. **批量模式**：一次性处理多个功能，AI 自动拆分、分析依赖、生成前趋图

**AI 自动提取技术约束**：

这是 spec 阶段最核心的能力。用户说我想要一个"远程车窗控制功能"，AI 会自动识别出：

- 需要CAN通信 → CAN信号定义（ID、周期、字节序）
- 需要云端通信 → MQTT协议
- 需要安全 → 命令加密、近场鉴权
- 需要状态监控 → DTC故障码定义

这些技术约束会自动写入规范文档，而不是让用户手动填写。

**技术方案选择**：

对于复杂功能，AI 会提供 3 套技术方案供用户选择：

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 方案 A | 简单快速 | 扩展性差 | 小型项目 |
| 方案 B | 平衡之选 | 无明显缺点 | 中型项目 |
| 方案 C | 扩展性强 | 复杂度高 | 大型项目 |

用户选择方案后，AI 会根据方案补充技术约束到规范文档。

### 4.2 az-sdd-coding：代码实现

**核心原则**：

我把这些原则打印出来贴在了工位上：

1. **规范先行**：coding 前必须先有已批准的规范。没有规范就不写代码。
2. **测试同步**：测试用例和代码同步编写，先写测试再写实现。
3. **CLI-First**：所有功能必须支持命令行，界面是可选的。
4. **自动化为主**：能自动化的绝不人工做。
5. **计划前置**：每次 coding 前生成执行计划，不是上来就写代码。

**TDD 流程**：

正确的 TDD 流程是这样的：

1. 读取规范中的测试用例
2. 编写测试代码（这时候测试应该失败，因为代码还没写）
3. 编写功能代码（让测试通过）
4. 重构优化（保持测试通过）

不是先写代码再补测试，而是**测试先行**。

**批量模式**：

当你要开发多个功能时，coding 会自动进入批量模式：

1. 检索所有未完成的功能规范
2. 分析功能间的依赖关系（比如"远程车门控制"依赖"CAN通信层基础模块"）
3. 生成功能实现前趋图（先做什么、后做什么）
4. 按顺序执行编码任务

### 4.3 az-sdd-test：测试验收

**Step 0 前置检查**：

在开始功能测试之前，必须先完成 Step 0：

- 应用启动脚本已创建并测试通过
- 应用关闭脚本已创建并测试通过

这一步是为了确保测试环境是可用的。如果启动脚本有问题，后面的测试都无法进行。

**测试执行**：

测试阶段会读取规范中的测试用例，生成一个交互式 HTML 验收页面。

为什么用 HTML 而不是命令行？因为**人工测试需要交互**。用户需要点击、输入、验证结果，HTML 页面比命令行更直观。

**localStorage 保存测试进度**：

如果测试中途被打断（比如开会），进度不会丢失。刷新页面后可以继续。

**状态更新**：

- 验收通过：待验收 → 已完成
- 验收不通过：待验收 → 开发中（回退）

回退时需要填写原因，比如"远程解锁功能在车载电压跌落时响应超时"。

### 4.4 az-sdd-rules：规则守卫

这是规则清单 SKILL。v3 中它不依赖平台自动加载，而是由 `/az-sdd-next` 或当前执行的 skill 显式检查。

**监控场景**：

1. 用户使用 az-sdd 系列 SKILL 时
2. 用户偏离 SDD 流程时（比如在没有规范的情况下尝试 coding）
3. SKILL 执行结果与预期不符时

**核心职责**：

1. 加载并记忆 az-sdd 规则配置
2. 监控 SKILL 执行是否符合规范
3. 必要时介入并纠正偏离行为
4. 提供规则查询和解释

**介入示例**：

比如你尝试在没有规范的情况下执行 coding，az-sdd-rules 会介入：

```
⚠️ 规则守卫提示：
当前状态：无可用规范
前置条件检查失败：az-sdd-coding 需要已批准（approved）状态的规范

建议操作：
1. 先使用 /az-sdd-spec 创建功能规范
2. 规范审核通过后（状态变为"已批准"）再执行 coding
```

## 五、项目档案目录结构

### 5.1 az-sdd/ 目录

```
az-sdd/
├── init.md              # 项目初始化信息（必填）
├── track.md             # 工作状态追踪记录（必填）
├── SPEC.md              # 功能规范索引目录（必填）
├── ARCH.md              # 技术规范索引目录（必填）
├── FEEDBACK.md          # 用户反馈索引目录（必填）
├── spec/                # 功能规范文档 *.spec.md
│   ├── 0010-远程车门控制.spec.md
│   └── 0011-远程车窗控制.spec.md
├── arch/                # 技术规范文档 *.arch.md
├── test/                # 测试文件目录
│   ├── cases/           # 测试用例
│   ├── reports/         # 测试报告
│   └── manuals/         # 操作手册
└── feedback/            # 用户反馈文档 FB-*.feedback.md
```

**必填文件说明**：

- `init.md`：项目基本信息（项目名称、描述、技术栈等）
- `track.md`：状态追踪记录，每次状态变更都要记录
- `SPEC.md`：功能规范索引，列出所有功能及其状态
- `ARCH.md`：技术规范索引，列出所有技术规范及其状态
- `FEEDBACK.md`：用户反馈索引，列出所有反馈及其处理状态

### 5.2 code/ 目录

```
code/
├── main.py              # 主入口（TBox应用层）
```

## 七、总结与延伸

### 7.1 关键知识点回顾

今天我们讲了 AZ-SDD 的实战内容：

**AZ-SDD 核心理念**：规范驱动开发，让用户只需描述业务，AI 自动完成全流程。

**9 个 SKILL**：
- init：初始化项目
- spec：编写功能规范
- arch：技术规范（可选）
- coding：代码实现
- test：测试验收
- track：状态追踪
- feedback：用户反馈
- rules：规则清单（显式检查）

**状态机**：9 个状态（草稿 → 审核中 → 已批准 → 开发中 → 测试中 → 待验收 → 已完成 → 已发布），组成完整生命周期。

**目录结构**：`az-sdd/` 存放规范文档，`code/` 存放代码文件，两者严格分离。
