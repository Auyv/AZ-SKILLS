# AZ-SDD-FEEDBACK

反馈自动闭环编排 - 用户主动调用后，AI 不只记录反馈，还要主动澄清、计划、执行、验证、关闭并沉淀经验。

## 日常使用边界

- 只有用户显式调用 `/az-sdd-feedback`、`az-sdd feedback`、`sdd feedback`，或明确要求“纳入 AZ-SDD 反馈闭环”时启用完整闭环。
- 普通“修 bug / 改需求 / 重构”仍优先直接对话处理，不自动进入 feedback。
- 一旦进入 feedback，本 skill 是闭环责任主体；`spec`、`arch`、`coder`、`tester` 是被编排的专业阶段。
- 自动化优先；只有需求不清、规范冲突、验收需要人工确认时才打断用户，且最多一次提出 1-3 个关键问题。

## 闭环目标

每条反馈必须从“用户描述”推进到明确结论：

```text
记录反馈 -> 澄清问题 -> 分类分流 -> 制定处理计划 -> 执行修复/变更
-> 测试验证 -> 关闭反馈 -> 经验沉淀
```

闭环完成前，反馈必须持续出现在 `az-sdd/FEEDBACK.md` 的未关闭列表中，并被 `/az-sdd-next` 优先提示。

## 状态流转

| 状态 | 含义 | 下一步 |
|------|------|--------|
| 待澄清 | 已创建反馈，但关键信息不足 | 询问 1-3 个关键问题，或自行复现 |
| 已计划 | 已判断类型并生成处理计划 | 按计划调用 spec/arch/coder/tester |
| 处理中 | 正在修复、改规范、重构或验证 | 持续更新处理记录 |
| 待验证 | 代码或规范处理完成，等待自动化/人工验证 | 执行测试或请求用户确认 |
| 已解决 | 验证通过或用户确认问题解决 | 写入经验沉淀并关闭 |
| 已关闭 | 不处理、重复、无法复现且已说明原因 | 记录关闭原因 |
| 待复现 | 暂无法复现，缺少必要条件 | 记录复现缺口和下一步等待项 |
| 转需求 | 反馈已转成新/改 spec，原反馈不再直接修复 | 关联 spec 并跟踪后续实现 |

## Step 0: 前置检查

1. 检查项目根目录是否存在 `az-sdd/`。
2. 若不存在，提示先使用 `/az-sdd-init` 初始化，不自行创建零散目录。
3. 若存在，读取：
   - `az-sdd/STATUS.md`
   - `az-sdd/FEEDBACK.md`
   - `az-sdd/SPEC.md`
   - `az-sdd/TRACK.md`
   - 可能相关的 `az-sdd/spec/*.spec.md`

## Step 1: 创建或更新反馈单

1. 生成反馈编号：`FB-{YEAR}-{SEQ}`，文件路径：`az-sdd/feedback/FB-{YEAR}-{SEQ}.feedback.md`。
2. 同步更新 `az-sdd/FEEDBACK.md` 索引。
3. 初始状态根据输入完整度设置：
   - 信息不足：`待澄清`
   - 信息足够：`已计划`
4. 反馈单必须包含：原始描述、问题场景、期望行为、影响等级、关联功能、下一步动作、处理计划、验证方式、关闭条件、经验沉淀。

## Step 2: 澄清与分类

根据用户描述自动判断反馈类型：

| 类型 | 判断信号 | 编排路径 |
|------|----------|----------|
| 实现缺陷 | 功能不工作、报错、表现与规范不一致 | `coder -> tester` |
| 验收异常 | 人工测试失败、测试单异常、用户验收不通过 | `tester -> coder -> tester` |
| 需求变更 | 期望行为与现有规范不同 | `spec -> coder -> tester` |
| 架构/重构 | 多模块影响、技术方案不适配、需要重构 | `arch -> coder -> tester` 或 `coder -> tester` |
| 新功能需求 | 现有规范不存在该能力 | `spec -> coder -> tester` |
| 无法处理 | 重复、无效、不处理、无法复现 | 记录原因并关闭或标记待复现 |

若信息不足，只问会影响执行路径的问题，例如：

```text
我需要确认 2 点后才能闭环处理：
1. 这个问题在哪个功能或页面出现？
2. 你期望它最终表现成什么样？
```

## Step 3: 输出反馈处理计划

执行任何修复或规范变更前，必须输出计划，并写入反馈单：

```markdown
## 反馈处理计划

| 项目 | 内容 |
|------|------|
| 问题判断 | {实现缺陷/需求变更/架构重构/验收异常/新功能/待复现} |
| 关联功能 | {功能编号和名称，未知则写待定位} |
| 下一步动作 | {coder/spec/arch/tester/none} |
| 任务拆解 | {1-5 个可执行任务} |
| 预计修改范围 | {代码/规范/测试/文档范围} |
| 验证方式 | {自动化测试/人工验收/复现步骤} |
| 关闭条件 | {测试通过/用户确认/转需求/无法复现说明} |
```

计划不要求用户确认，除非存在需求冲突、规范改动或高风险重构。

## Step 4: 编排执行

### 实现缺陷

1. 将反馈状态改为 `处理中`。
2. 定位相关规范和代码。
3. 调用 `/az-sdd-coder` 的修复路径，要求读取反馈单作为上下文。
4. 修复完成后记录：
   - 修改摘要
   - 关联 coder 计划
   - 自动化测试命令和结果
5. 进入 `待验证` 或 `已解决`。

### 验收异常

1. 读取相关测试单和规范。
2. 调用 `/az-sdd-tester` 的异常处理流程。
3. 若确认是实现缺陷，转入 coder 修复后再回到 tester。
4. 若确认是规范问题，转入 spec 更新。
5. 未验证通过前不得关闭反馈。

### 需求变更或新功能

1. 先调用 `/az-sdd-spec` 创建或更新规范。
2. 将反馈状态改为 `转需求` 或 `处理中`，并关联 spec。
3. 规范批准后再调用 `/az-sdd-coder`。
4. 实现后调用 `/az-sdd-tester` 验证。

### 架构或重构问题

1. 判断是否需要独立技术规范。
2. 需要技术决策时调用 `/az-sdd-arch`；仅代码结构调整时调用 `/az-sdd-coder` 重构路径。
3. 重构完成后必须运行回归测试。
4. 记录重构范围、风险和验证结果。

### 无法复现或不处理

1. 不调用 coder/tester。
2. 写入已尝试复现步骤、缺失条件、关闭或挂起原因。
3. 状态设为 `待复现` 或 `已关闭`。

## Step 5: 测试验证

- 优先运行项目已有自动化测试命令。
- 如果反馈涉及人工体验、界面或验收项，生成或复用 `/az-sdd-tester` 工单。
- 修复后测试失败时，反馈保持 `处理中`，记录失败原因并继续修复。
- 只有测试通过、用户确认、转需求完成、明确不处理或待复现挂起时，才允许结束闭环。

## Step 6: 关闭与经验沉淀

闭环结束时必须更新反馈单和 `FEEDBACK.md`：

```markdown
## 闭环结论

| 字段 | 内容 |
|------|------|
| 最终状态 | 已解决/已关闭/待复现/转需求 |
| 处理方式 | 修复/改规范/重构/不处理/无法复现 |
| 关联产物 | spec/coder/tester/commit/验证证据路径 |
| 验证证据 | 测试命令、测试工单、用户确认 |
| 关闭时间 | {DATETIME} |

## 经验沉淀

- 根因：{ROOT_CAUSE}
- 解决方式：{SOLUTION}
- 验证证据：{EVIDENCE}
- 预防建议：{PREVENTION}
```

推进或关闭反馈时更新 `az-sdd/STATUS.md` 的当前焦点、未闭环反馈或阻塞项，并向 `az-sdd/TRACK.md` 追加关键问题事件，尤其是高优先级问题、重复问题、架构问题和重构问题。

## 与其他 Skill 的联动

```text
/az-sdd-feedback
  -> 记录反馈并生成计划
  -> 按类型编排：
     - 实现缺陷：az-sdd-coder -> az-sdd-tester
     - 验收异常：az-sdd-tester -> az-sdd-coder -> az-sdd-tester
     - 需求变更：az-sdd-spec -> az-sdd-coder -> az-sdd-tester
     - 架构/重构：az-sdd-arch 或 az-sdd-coder -> az-sdd-tester
     - 无法复现/不处理：记录原因并关闭或挂起
  -> 回写 STATUS.md、FEEDBACK.md、feedback 单，必要时追加 TRACK.md
  -> 输出闭环摘要和经验沉淀
```

## 输出要求

每次 feedback 闭环结束时，最终回复必须包含：

1. 反馈编号和最终状态。
2. 问题判断和处理路径。
3. 实际修改或转需求内容。
4. 测试验证结果。
5. 是否已关闭，以及关闭依据。
6. 经验沉淀摘要。

## 错误处理

| 情况 | 处理方式 |
|------|----------|
| `az-sdd/` 不存在 | 提示先初始化，不创建孤立反馈 |
| 反馈内容不明确 | 最多问 1-3 个关键问题 |
| 找不到关联规范 | 搜索相近功能；仍无结果则按新需求进入 spec |
| 修复后测试失败 | 保持 `处理中`，记录失败并继续修复 |
| 连续无法复现 | 标记 `待复现`，记录复现缺口 |
| 用户要求不处理 | 标记 `已关闭`，必须写明关闭原因 |
| 需求变更较大 | 标记 `转需求`，关联新/改 spec |
