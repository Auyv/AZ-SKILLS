一、AI Coding 的三阶段

阶段时间代表工具核心能力局限性

1.1 第一阶段：AI 辅助编程（2019-2022）

故事背景

2019 年，GitHub 推出了 Copilot 的技术预览版。写 HTTP 请求封装函数时，第三行代码就开始自动补全，包括异常处理。

感受：AI 好像真的懂我在写什么。

代表工具

  • GitHub Copilot、Tabnine、Kite

核心交互方式

IDE 插件，代码补全。你写函数名、注释，AI 自动补全剩余代码。

解决了什么问题

效率问题——重复代码不用再手动敲了。

# 我只需要写这几行：
def get_user
# AI 自动补全：
def get_user(user_id: int) -> dict:
    """Get user by ID."""
    return db.query(f"SELECT * FROM users WHERE id = {user_id}")

局限性

  • 只能生成单点代码片段——AI 不知道函数在项目中的角色
  • 无全局理解能力——上下文只有当前编辑的文件
  • 复杂逻辑帮不上忙——需要先把逻辑设计好

AI 是个好助手，但只是个助手。

1.2 第二阶段：AI 对话编程（2022-2024）

故事背景

2022 年 11 月 ChatGPT 上线。可以用自然语言描述需求，AI 给出完整实现方案。

原来编程可以用自然语言。

代表工具

ChatGPT、Claude、Cursor、Copilot Chat

核心交互方式

对话窗口，自然语言描述需求。你可以"告诉"AI 你要做什么，而不是手动写代码。

解决了什么问题

设计问题——你不需要从第一行代码开始写起了。

帮我实现远程车窗控制功能：
1. 支持四门独立升降控制
2. 支持防夹手功能
3. 支持限位停止
4. 状态变化时实时上报云端

比第一阶段强在哪里

维度第一阶段第二阶段
生成粒度单函数功能模块
理解能力代码前缀自然语言描述
迭代方式重写对话修改

局限性

  • 上下文窗口有限——AI 只记得最近 N 条对话
  • 多文件协作能力弱——不理解文件间的依赖关系
  • 缺乏项目规范约束——每次对话独立，代码风格可能不一致
  • 自然语言有歧义性——"发送车门状态"可能有多种理解

AI 是个聪明的助手，但它不懂你的项目。

1.3 第三阶段：AI 规范驱动编程（2024-）

故事背景

2024年中，TBox项目有5个开发人员同时工作，问题很快出现：

  • 开发者A的CAN信号ID是0x201，开发者B定义的是0x301，ID冲突
  • 每个人对"远程控制"的理解都不一样
  • 三个月后，同一个功能有三种不同实现

需要一个统一的东西来约束AI。

核心理念

不再是"告诉 AI 要做什么"，而是"先让 AI 理解我们要做什么、有什么约束、交付标准是什么"。

需求描述 → 规范文档(Spec) → 技术约束 → 代码实现 → 测试验收

核心升级

AI 不仅生成代码，还能理解项目规范、遵循技术约束、维护状态。

二、各阶段的问题与解决

痛点对比

维度第一阶段第二阶段第三阶段
输入形式代码前缀自然语言需求结构化规范文档
生成粒度单函数/单文件功能模块完整功能
上下文范围当前编辑文件最近N条消息完整项目规范
一致性保证无保证依赖prompt质量规范强制约束
测试无手动补充规范内置测试用例
协作无无多人共享规范

第二阶段痛点：多人协作

5个开发者分别描述"车窗控制"，得到5套不同设计方案：

  • 信号ID各不相同
  • 字节序定义不一致
  • 没有测试用例

第三阶段解决思路：

  • 规范文档统一规定CAN信号ID、周期、字节序
  • 规范内置测试用例
  • 记录状态追踪

三、为什么需要 Spec？

3.1 自然语言的歧义性问题

"远程开锁"在TBox开发中，可能有几种理解？

  • 车主手机APP远程解锁车门
  • 4S店技师近场诊断时解锁OBD接口
  • 车队管理员解锁运营车辆
  • 二手车交易时的解锁权限变更
  • 交警/保险公司应急解锁
  • 车辆休眠后的唤醒解锁

同一功能描述，在汽车行业可能有完全不同的业务上下文。

Spec通过精确定义功能边界来消除歧义

## 功能边界

### 做什么
- 支持车主APP远程解锁车门（限定距离：无限制）
- 支持蓝牙近场解锁（距离车辆5米内）
- 解锁成功后车辆进入ready状态

### 不做什么
- 不支持4S店远程解锁（需走诊断CAN总线）
- 不支持应急解锁（将由紧急救援模块处理）
- 不支持营运车队远程强制解锁

### 权限约束
- 仅车主持有解锁权限
- 解锁记录需同步至云端
- 单日解锁次数上限：10次

3.2 多人协作的认知对齐

最糟糕的情况：产品提了一个需求，5个开发人员各自开发，集成时发现——

  • 开发者A的"远程空调"包含了座椅加热
  • 开发者B的"远程空调"只有制冷和制热
  • 开发者C的"远程空调"还有除雾功能
  • CAN报文里三个不同的信号定义，ID各不相同

Spec作为唯一的真实来源，所有人基于同一份文档工作。

Spec统一CAN信号定义

## CAN信号定义（空调控制）

### 空调控制信号：AC_CTRL_0x123
| 信号名   | 字节位置  | 位定义   | 值范围  | 说明        |
|----------|----------|---------|--------|-------------|
| ac_power | 0[0]     | 1bit    | 0/1    | 空调电源状态 |
| ac_mode  | 0[1-3]   | 3bit    | 0-4    | 0:关闭 1:制冷 2:制热 3:自动 4:除雾 |
| ac_temp  | 1[0-7]   | 8bit    | 16-30  | 目标温度(℃) |
| fan_speed| 2[0-5]   | 6bit    | 0-7    | 风扇转速等级 |

3.3 测试用例缺失

AI生成的代码，在第二阶段只能手动写测试用例。但汽车行业的测试不是那么简单：

  • 不能"随便测测"，TBox是要上车的，出了bug可能涉及人身安全
  • 不能只测功能，还要测CAN通信、诊断协议、故障注入
  • 不能只测"正常情况"，还要测"极端环境"（低温启动、高温休眠）

Spec内置测试用例，AI生成代码后自动运行验收。

Spec内置测试用例

## 测试用例

| 用例编号 | 用例名称               | 测试类型   | 验证结果 |
|----------|----------------------|-----------|----------|
| MT001    | 远程解锁命令下发成功    | HIL自动化  | 待验证   |
| MT002    | 信号超时（500ms无响应） | HIL自动化  | 待验证   |
| MT003    | 车内CAN总线故障时安全策略 | 人工测试 | 待验证   |
| MT004    | 低温-40℃环境解锁功能   | 环境测试   | 待验证   |
| MT005    | 高频解锁请求（10次/分钟）| 自动化    | 待验证   |

3.4 大型项目的维护性

半年后，这些问题出现了：

  • 第一个功能是谁开发的、原始需求是什么，没人记得了
  • AI当时为什么这样定义CAN信号ID，不清楚
  • 新需求来了不知道怎么和现有CAN信号兼容
  • 有bug不敢改，怕影响其他功能
  • 客户要做GB/T32960认证，不知道哪些代码需要审查

Spec文档记录所有设计决策

Spec文档记录了：

  • CAN信号定义
  • 故障诊断协议
  • 安全策略
  • 行业标准合规性

新人可以通过阅读Spec快速理解TBox的功能架构，而不是去读那几千行没有注释的C代码。

四、Spec 规范的核心组成

4.1 功能边界

回答一个问题：这个功能做什么、不做什么？

## 功能边界

### 核心功能
1. 车主APP远程解锁车门
2. 蓝牙近场解锁（距离车辆5米内）
3. 解锁成功后整车进入ready状态

### 边界情况处理
- 车辆处于碰撞报警状态时，拒绝解锁
- 网络信号弱时，解锁请求超时时间延长至3秒
- 单日解锁次数超过10次时，触发风控审核

### 不包含的功能
- 4S店诊断模式解锁
- 营运车队强制调度解锁
- 远程鸣笛/闪灯

4.2 技术约束

回答问题：用什么协议、有什么通信要求、安全策略？

## 技术约束

### 通信协议
- TBox与云平台：MQTT over TLS 1.2
- TBox与车载CAN：HS-CAN 500kbps（符合ISO 11898）
- 近场解锁：BLE 4.2

### CAN信号定义
- 车门状态信号：DOOR_STATUS_0x101（周期100ms）
- 解锁命令信号：DOOR_UNLOCK_0x102（事件触发）
- TBox心跳信号：TBOX_HEARTBEAT_0x100（周期1s）

### 安全约束
- 命令使用AES-256加密
- OTA升级需双重签名验证
- 解锁记录完整上云，不可篡改

### 实时性要求
- 云端命令下发到CAN信号输出：<500ms
- 近场解锁响应时间：<200ms

4.3 验收标准

回答问题：怎么算做完了？

## 验收标准

### 功能验收
- [ ] 车主APP可远程解锁车门
- [ ] 解锁命令成功触达CAN总线
- [ ] 云端日志记录完整

### 行业标准要求
- [ ] 符合GB/T 32960（新能源汽车远程服务与管理）
- [ ] 通过EMC测试（电磁兼容性）

### 性能要求
- 云端到CAN信号输出延迟：<500ms
- 支持100并发解锁请求

### 可靠性要求
- -40℃～+85℃环境下功能正常
- 连续1000次解锁操作无故障

五、从 Spec 到代码的流程

5.1 标准流程

需求描述 → Spec 规范 → 技术审核 → 代码实现 → 测试验收 → 状态更新
    ↓         ↓       ↓          ↓           ↓
  用户      AI+用户   产品+技术    AI+规范     规范+测试

5.2 流程详解

第一步：需求描述

用户用自然语言描述需求

第二步：Spec 规范

AI提取功能边界和技术约束，生成规范文档

第三步：技术审核

技术负责人审核确认CAN信号定义等

第四步：代码实现

AI按照规范文档生成代码，不会擅自决定CAN信号ID

第五步：测试验收

运行规范文档中内置的测试用例验证

第六步：状态更新

更新规范文档中的状态字段

5.3 为什么这个流程能解决问题？

我们之前提到的问题解决方案
自然语言歧义性Spec 精确定义功能边界，消除歧义
多人认知不一致统一规范文档，所有人基于同一份文档工作
测试用例缺失Spec 内置验收测试用例
技术债务累积Spec 记录技术约束，新功能必须遵循
流程不透明状态机追踪，每个阶段清晰可见
代码不一致AI 严格按规范生成，强制一致性

六、总结与练习

关键知识点回顾

第一部分：AI Coding 三阶段

阶段时间代表工具核心能力局限
辅助编程2019-2022Copilot代码补全单点代码
对话编程2022-2024ChatGPT自然语言生成无项目理解

第二部分：为什么需要 Spec

  1. 消除自然语言的歧义性
  2. 统一多人协作的认知
  3. 内置测试用例保证质量
  4. 记录设计决策便于维护

第三部分：Spec 核心组成

  1. 功能边界（做什么、不做什么）
  2. 技术约束（技术栈、API 规范、安全要求）
  3. 验收标准（测试用例、性能要求）
  4. 状态追踪（当前阶段、阻塞问题）

思考题

  1. 在你的项目中，是否遇到过AI生成代码与预期不一致的问题？原因是什么？
    提示：可能是自然语言歧义性，可能是缺乏规范约束，也可能是CAN信号定义不明确

  2. 如果让你为一个TBox的"远程空调控制功能"编写Spec，你会关注哪些方面？
    提示：功能边界——做什么不做什么；CAN信号定义；故障安全策略；行业标准符合性

  3. Spec规范相比普通需求文档，在TBox开发中最大的区别是什么？
    提示：精确的CAN信号定义、故障诊断协议、安全约束、行业标准合规性
