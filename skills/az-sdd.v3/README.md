# AZ-SDD v2 — 规范驱动开发 Skills 系统

基于 SDD（Spec-Driven Development）理论的 AI 辅助开发流程。

## 核心理念

```
需求 → 规范（含技术约束） → 代码 → 测试验收 → 追踪 → 反馈
```

**让用户只需描述业务，AI 自动提取技术要素。**

---

## SKILL 体系（8个）

| SKILL | 命令 | 阶段 | 说明 |
|-------|------|------|------|
| az-sdd-init | `/az-sdd-init` | 项目初始化 | 创建 az-sdd 档案目录结构 |
| az-sdd-spec | `/az-sdd-spec` | 功能规范 | 编写功能规范（含 AI 提取的技术约束） |
| az-sdd-arch | `/az-sdd-arch` | 技术规范（可选） | 为复杂技术决策创建独立文档 |
| az-sdd-coding | `/az-sdd-coding` | 代码实现 | 按照规范实现功能代码（支持批量开发、自动分析依赖、生成前趋图） |
| az-sdd-test | `/az-sdd-test` | 测试验收 | 交互式人工测试验收（自动检索测试用例、CheckList引导、负责人签名、版本履历） |
| az-sdd-track | `/az-sdd-track` | 状态追踪 | 管理项目工作状态 |
| az-sdd-feedback | `/az-sdd-feedback` | 用户反馈 | 智能反馈处理（Bug自动修复、改进建议确认、需求规范创建） |
| **az-sdd-rules** | `/az-sdd-rules` | 规则守卫 | **自动加载**，监控 SKILL 执行是否符合规范，发现偏离时介入纠正 |

## az-sdd-rules 规则守卫

**自动加载**，无需手动触发。当用户使用任何 az-sdd-* SKILL 时自动介入。

### 核心职责

| 职责 | 说明 |
|------|------|
| 加载规则 | 启动时将规则配置加载到记忆 |
| 监控流程 | 确保 SKILL 按正确顺序执行 |
| 状态校验 | 确保状态变更符合转换规则 |
| 干预纠正 | 发现偏离时及时介入 |
| 解释规则 | 应要求解释规则含义 |

### 强制介入场景

| 场景 | 偏离行为 | 处理方式 |
|------|---------|---------|
| 跳过 spec 直接 coding | spec → coding 未满足条件 | 阻止并询问 |
| 状态跳跃 | 未按顺序经历状态 | 阻止并提示正确顺序 |
| 审核未通过继续开发 | reviewing → developing | 阻止并提示审核要求 |
| 测试未完成提前验收 | testing → acceptance | 阻止并提示等待测试 |

### 警告介入场景

| 场景 | 处理方式 |
|------|---------|
| 复杂功能跳过 arch | 建议创建技术规范 |
| 回退未记录原因 | 要求记录到 track.md |

## 快速开始

### 1. 初始化项目

```
/az-sdd-init
```

### 2. 描述功能需求

```
/az-sdd-spec
```

**支持两种输入方式**：

1. **单个功能**：直接描述一个功能需求
2. **批量功能**：一次性描述多个功能，AI 自动拆分并逐个生成规范

**单个输入示例**：
```
我需要一个用户登录功能...
```

**批量输入示例**：
```
我想做这几个功能：
1. 用户可以注册和登录
2. 登录后可以看到任务列表
3. 任务可以设置截止日期

另外还需要：
- 任务可以添加标签
```

AI 会自动识别并拆分多个功能，逐一确认后批量生成规范文档。

### 3. （可选）补充技术规范

```
/az-sdd-arch
```

### 4. 开始编码

```
/az-sdd-coding
```

**支持两种开发模式**：

1. **单个开发**：指定一个功能编号，按规范逐步实现
2. **批量开发**：AI 自动检索所有未完成的功能，分析依赖关系，生成前趋图，按批次执行

**coding 阶段核心原则**：

```
1. 规范先行 - 检查功能规范和技术规范后才开始开发
2. 测试同步 - 编写代码时同步更新测试用例
3. CLI-First - 除界面交互外，所有功能必须支持 CLI
4. 自动化为主 - 自动化测试时跳过人工验证，过度依赖人工测试会反馈给规范
5. 最小交互 - 全程只与用户交流 1-3 次，除非有矛盾或不清楚的问题
6. 计划前置 - 展示开发计划，用户同意后再动手
```

### 5. 测试验收

```
/az-sdd-test
```

**交互式人工测试流程**：

```
用户触发 → 自动检索待测试功能 → 生成 CheckList → 用户逐一验证打钩
                                                   │
                                                   ↓
                       未全部通过 ← 验证是否全部通过 ← 填写签名
                                                   │
                                                   ↓
                             AI 更新状态 ← 全部通过 ← 允许提交
                                                   │
                                                   ↓
                                           生成版本更新履历
```

**核心规则**：
- 自动检索需要人工验证的测试用例（MT001, MT002...）
- 生成可交互的 HTML CheckList 页面
- 必须全部打钩才能提交
- 填写测试负责人签名
- AI 自动更新规范状态 + 生成 CHANGELOG

### 6. 更新状态

```
/az-sdd-track
```

### 7. 智能反馈处理

```
/az-sdd-feedback
```

**面向用户的智能反馈系统**：

```
用户提交反馈
     │
     ├── 🐛 Bug ──────────→ 自动触发 Coding 修复
     │
     ├── 💡 改进建议 ──────→ 解释原设计 → 确认是否变更
     │                              │
     │                              ├── 需要变更 → 触发 Spec 更新
     │                              │
     │                              └── 不需要 → 记录关闭
     │
     └── ✨ 新功能需求 ─────→ 检测现有规范
                              │
                              ├── 存在类似 → 询问差异
                              │
                              └── 不存在 → 触发 Spec 新增
```

## 状态定义（9个状态）

```
草稿 → 审核中 → 已批准 → 开发中 → 测试中 → 待验收 → 已完成 → 已发布
```

| 状态 ID | 中文名称 | 图标 |
|---------|---------|------|
| draft | 草稿 | 📋 |
| reviewing | 审核中 | 👁️ |
| approved | 已批准 | ✅ |
| developing | 开发中 | 🔨 |
| testing | 测试中 | 🧪 |
| acceptance | 待验收 | 🎯 |
| completed | 已完成 | ✅ |
| released | 已发布 | 🚀 |
| blocked | 阻塞 | 🚧 |
