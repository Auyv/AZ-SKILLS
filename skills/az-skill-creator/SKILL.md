# AZ 技能创建器

把用户目标转化为范围清晰、容易触发、能够实际执行的技能。默认保持轻量；只有复杂度和风险确有需要时才增加脚本、文档、错误契约和完整测试矩阵。

## 核心原则

- 优先从用户请求、当前对话、仓库规则和现有文件中推断信息。只有缺失信息会实质改变结果或权限边界时，才集中提出少量问题。
- 把 Skill 视为 Agent 的决策与执行指南，不默认把它设计成 RPC/API。仅当调用方确实需要稳定机器接口时定义完整 `inputs`、`outputs`、错误码或统一响应结构。
- 最小有效交付是一个包含有效 YAML front matter 和执行指引的 `SKILL.md`。
- 目录和文件必须有实际用途。不要为了结构完整而创建空的 `docs/`、`assets/`、`scripts/`、`evals/` 或 `MANUAL.md`。
- 细节与风险匹配：普通提示型技能保留决策空间；高风险、脆弱或重复执行的流程使用更明确的步骤、验证和停止条件。
- 保留用户范围和权限边界。创建技能不自动授权安装依赖、修改外部系统、登记发布、同步或提交代码。

### 工作流型 Skill

工作流不是另一种制品，而是 Skill 的一种形态：当任务包含多个可复用阶段、状态门槛、人工确认或交接点时，在普通 Skill 的基础上增加阶段编排。统一在 AZ-SKILLS 的 `skills/<name>-workflow/` 下管理，并沿用相同的发现、manifest、同步和版本流程。

- 只有步骤会重复出现、顺序或安全门禁具有复用价值，且用户明确要求固化或确认长期复用时，才创建工作流型 Skill；一次性任务、未经验证的尝试和项目专属临时配置不固化。
- Skill 负责触发范围、阶段顺序、上下文判断、人工门禁、重试/停止条件和交接产物。
- 执行能力优先由现有 MCP 工具提供；Skill 只描述如何选择和组合工具，不为已有 MCP 能力重复创建本地包装脚本。
- MCP 负责确定性执行、参数校验、结构化结果和可观察错误；若没有合适的 MCP，且流程确实需要跨平台一致的确定性处理，才按 Python 脚本策略补充实现。
- 工作流技能仍必须先满足最小交付：一个有效的 `SKILL.md`。只有阶段复杂度、风险或脱离 Agent 的手工交接确有需要时，才增加 `references/`、`MANUAL.md`、脚本或测试矩阵。

## 选择工作模式

### 快速创建模式（默认）

适用于规则型、写作型、评审型、路由型以及低风险的简单工具技能。

1. 读取当前仓库规则、用户上下文和待优化技能；能推断的内容直接采用合理默认值。
2. 确定技能名称、触发场景、目标、关键约束和执行边界。
3. 创建或更新简洁的 `SKILL.md`。
4. 仅在能显著提高可靠性时添加资源或少量 eval。
5. 做结构和内容检查，直接交付简短结果摘要。

快速模式不默认逐项访谈输入、输出和异常，不逐轮展示草稿，也不要求用户反复确认满意度。

### 工程化模式

满足以下任一条件时启用：

- 涉及外部工具、网络服务、设备、数据库或第三方 API。
- 涉及文件解析、格式转换、批量处理或跨平台一致执行。
- 存在安全、隐私、权限、不可逆操作或较高误操作风险。
- 存在复杂失败恢复、状态迁移或容易出错的脆弱流程。
- 用户明确要求严格测试、正式发布或团队长期维护。

工程化模式按实际需要增加：

- 明确的输入、输出、前置条件、权限边界和停止条件。
- 可操作的错误处理、恢复策略和必要错误码。
- 覆盖主要正常路径、关键边界和高风险失败场景的测试矩阵。
- 有明确复用价值的脚本、参考资料、模板或操作手册。
- 发布前的实际运行、基线对比或独立评估。

即使进入工程化模式，也不要机械生成与技能无关的通用错误码或目录。

## 名称与触发范围

- 用户明确指定名称时优先保留；新名称只允许小写字母、数字和连字符，并应与目录名一致。
- 用户未指定名称时，根据核心动作生成简短名称，AZ 自有通用技能默认使用 `az-` 前缀。
- 优化现有技能时不得擅自修改目录名或 front matter 的 `name`。用户明确要求改名时，先检查 manifest、文档和其他调用方的引用，说明影响并确认迁移范围。
- `description` 必须简洁说明“做什么、何时使用”，必要时写明容易误触发的排除场景。不要堆砌关键词或吸引无关请求。
- 触发范围应覆盖真实用户表达，但不得使用“处理所有相关任务”一类泛化描述。

## 交付范围与创建位置

先识别目标环境的技能加载规则，不要把任意项目中的 `skills/` 目录默认视为可加载目录。

在 AZ-SKILLS 仓库中工作时，`skills/` 是所有技能（包括工作流型 Skill）源码的单一真相来源，新建和更新都应先落在这里。其他环境按以下顺序判断：

1. 检查工作区说明、项目配置、已暴露技能列表以及 `.agents/`、`.codex/` 等约定。
2. 已确认项目技能加载目录时，创建为 `项目可加载技能`。
3. 未发现加载规则时，只有目标位置会影响交付时才集中询问：创建 `项目内技能草稿/源码包`，还是写入明确指定的全局技能目录。
4. 写入全局目录前复述目标路径并取得明确同意。

交付时使用以下术语之一：

- `项目可加载技能`：已按当前 Agent 的项目加载规则创建。
- `项目内技能草稿/源码包`：仅作为项目文件交付，不承诺自动加载。
- `全局技能`：写入全局技能目录，供后续会话加载。

说明实际路径、加载依据，以及是否需要重启或新开会话。

## 资源设计

### SKILL.md

始终创建。保留共享目标、模式选择、关键约束、核心流程以及资源路由。详细且只在特定场景使用的内容放到配套文档，避免所有调用都加载无关上下文。

可参考 [template/SKILL.template.md](template/SKILL.template.md)，但按任务删减，不保留占位内容。

### Python 脚本

当流程可确定、可重复，需要稳定解析、批量处理或跨平台一致执行时，优先考虑封装为 Python 脚本：

- Agent 负责语义理解、上下文判断、方案选择和权限确认。
- Python 负责确定性解析、转换、校验、批处理和可重复执行。
- 优先使用 Python 标准库。引入第三方依赖时，说明必要性、安装要求和无依赖时的降级方案。
- 新增或修改脚本后，运行有代表性的测试并保留原始错误。
- 不要把一次性命令、简单文件写入或纯语义判断包装成脚本，也不要仅为填充 `scripts/` 目录而创建代码。
- 如果现有 MCP 已覆盖执行能力，优先调用 MCP；不要为了让工作流目录看起来完整而重复实现同一能力。

### 其他资源

- `docs/` 或 `references/`：仅存放特定模式才需要的规范、详细流程或领域资料，并从 `SKILL.md` 明确说明何时读取。
- `assets/`：仅存放生成结果会复用的模板、图片、字体或工程骨架。
- `MANUAL.md`：仅当用户需要脱离 Agent 手工执行，或操作流程需要独立维护时创建。
- `evals/`：按风险和行为复杂度创建。普通技能可使用少量代表性用例；严格模式覆盖主路径、关键边界、高风险失败和必要降级。

## 创建与优化

### 创建新技能

1. 从上下文提取目标、触发条件、成功标准和真实约束。
2. 选择快速或工程化模式，并仅在判断会影响产物时简短说明原因。
3. 确定名称、交付范围和目标路径；只有这些信息无法安全推断时才集中提问。
4. 先完成最小可用的 `SKILL.md`，再按价值增加资源。
5. 检查触发描述是否准确、规则是否改变 Agent 决策、边界是否可执行、资源是否被正确路由。

若技能是工作流型 Skill，额外确认目录使用 `<name>-workflow` 命名，阶段之间的输入/输出和交接点清楚，并明确哪些步骤由 MCP 执行、哪些判断由 Agent 完成。

### 优化现有技能

1. 完整读取现有 `SKILL.md` 及本次修改涉及的资源，检查调用方和 manifest 引用。
2. 找出真实使用问题：误触发、漏触发、交互冗余、规则冲突、上下文膨胀、不可执行步骤或测试缺口。
3. 优先做窄而有效的修正，删除重复的通用建议和无价值脚手架，保留兼容性及用户未要求改变的行为。
4. 对脚本和高风险流程执行相称验证；普通文档型改动不强制制造完整测试矩阵。

## 测试策略

测试数量由风险决定，不设所有技能统一的最低数量：

- 低风险技能：验证 front matter、名称、触发范围、核心流程和未完成占位符；必要时增加 1～3 个代表性 eval。
- 中等复杂度技能：覆盖主要正常路径、一个容易误触发的场景和关键失败路径。
- 工程型或高风险技能：建立完整测试矩阵，覆盖主路径、边界、权限/依赖失败、恢复策略和停止条件；能安全运行时执行真实验证。

测试应检查可观察行为和关键不变量，不要只匹配固定措辞、标题或正则表达式。只有复杂度和风险值得时才使用子代理或无技能基线对比。

## 创建与发布分阶段

### 创建阶段

创建或更新技能源码，完成必要验证并报告交付范围。默认到此结束。

### 操作边界

| 操作 | 默认行为 | 需要的授权 |
| --- | --- | --- |
| 评估/测试 | 只读检查，不修改技能、manifest 或目标平台 | 用户请求评估即可 |
| 创建/优化 | 修改 `skills/` 下源码，完成相称验证 | 用户明确要求创建或修改 |
| 登记/同步 | 修改用户本地 `manifest.yaml`，执行 dry-run 或正式同步 | 用户明确要求发布、登记或同步 |
| 删除/改名/迁移 | 先列出影响范围和回滚方式，再执行 | 用户明确授权具体范围 |

在 AZ-SKILLS 仓库中，`manifest.yaml` 只作为用户本地平台适配文件；仓库仅提供 `manifest.yaml.demo` 示例。创建阶段不得因为技能源码已完成就自动生成、登记或同步 manifest。

### 发布阶段

只有用户明确要求正式发布、同步到 Agent，或当前请求已清楚包含发布时才执行：

1. 确认用户已从 `manifest.yaml.demo` 创建本地 `manifest.yaml`，并按目标平台登记技能。
2. 先运行结构检查和 `python sync_skills.py --dry-run`。
3. 检查将新增、更新或删除的目标文件，避免覆盖无关内容。
4. 运行正式同步，并验证源码目录与目标 Agent 中的技能一致。
5. 未经明确同意不得 commit 或 push。

发布失败时保留源码和清单修改，报告执行命令及原始错误，不用绕过参数掩盖问题。

## 完成检查

- `SKILL.md` 存在，front matter 至少包含 `name`、`description`、`version`。
- 目录名、`name` 和 manifest 引用一致；触发描述具体且不过度泛化。
- 快速/工程化模式选择与实际风险一致，没有强制生成无价值文件。
- 新增资源都被入口文档正确引用，未留下模板占位符或重复内容。
- Python 脚本确有确定性复用价值，依赖和降级策略明确，并已做相称验证。
- 发布动作有明确授权；最终说明修改文件、验证结果、实际交付范围和加载状态。
